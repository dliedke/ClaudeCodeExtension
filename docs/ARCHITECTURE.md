# Architecture — Key Non-Obvious Details

> On-demand reference. Read the relevant section before editing the file it describes
> (see the index in `CLAUDE.md` → Architecture). These are the non-obvious gotchas and
> design decisions that aren't apparent from the code alone.

## Terminal Embedding (Terminal.cs)

- Two terminal modes: Command Prompt (conhost) and Windows Terminal (wt.exe), via `_settings.SelectedTerminalType`
- Lifecycle serialization: `_terminalLifecycleSemaphore` prevents overlapping start/stop transitions. On top of it, `_terminalLaunchTicket` (monotonic, incremented per `StartEmbeddedTerminalAsync` call) makes queued duplicate launches collapse: a launch that finds a newer ticket after acquiring the semaphore skips itself ("skipping superseded launch request" in the launch log), and the relaunch-retry loop aborts its remaining backoff attempts when a newer request queues up behind it (no MessageBox in that case). Without this, every queued launch tore down the terminal the previous one had just embedded — WSL stop/start churn that feeds the issue #73 failure modes
- Session ID tracking: `_terminalStartupSessionId` discards stale startup work when a new terminal start is triggered before the old one finishes
- `SetParent()` retry: Up to 3 attempts with 200ms delay and Win32 error logging (`Marshal.GetLastWin32Error()`), re-applies window styles between retries
- Conhost handle discovery: `FindMainWindowHandleByConhostAsync()` retries with 5s then 10s timeouts; uses ToolHelp32 (`CreateToolhelp32Snapshot`) for child PID lookup. Accepts only `ConsoleWindowClass` windows — a PID match alone can hit other top-level windows reporting the same PIDs (e.g. the conhost thread's invisible "Default IME" window), and embedding one of those leaves the panel blank while the real console floats (issue #73). Aborts early when the launcher process has exited
- Unified relaunch retry + launch log (issue #73): the conhost path in `StartEmbeddedTerminalAsync` wraps the entire spawn→find→embed unit in a bounded relaunch loop (`relaunchBackoffMs = {0, 750, 1500, 3000, 6000}`, 5 attempts since 10.98 — a 10.97 log showed WSL teardown contention outlasting the original ~2s ladder by minutes). Reproduced on the author's own machine 2026-06-11: two transient, WSL-only failure modes that clear within ~1 min, both triggered by switching solutions/providers while the just-stopped `wsl bash` session is still tearing down — (A) conhost spawns then exits immediately with `exitCode=0` (no window), and (B) the window is found but the conhost dies mid-embed so `SetParent` fails repeatedly with Win32 error 1400 (`ERROR_INVALID_WINDOW_HANDLE`). Both now relaunch instead of giving up: between attempts `StopExistingTerminalAsync()` kills the orphan window/process (so retries don't pile up live conhosts) then backs off. The inner spawn loop still re-spawns once on immediate exit; no inner retry when the launcher is alive but windowless (would pile up live terminals — that case defers to the outer relaunch via cleanup). Console color/font registry is saved once before the loop and restored once after (re-saving per attempt would clobber the originals). Only after all relaunch attempts fail does a MessageBox appear. Launch steps (teardown, spawn PID, whether VS had a console attached, find/SetParent failures with Win32 errors, exit codes) append to `%LocalAppData%\ClaudeCodeExtension\terminal-launch.log` via `LogTerminalLaunch()` (best-effort, never throws, resets at 512 KB) — `Debug.WriteLine` is compiled out of Release builds, so this log is the only way to diagnose user machines; ask reporters to attach it
- Embed failure honesty + panel self-repair (issue #73): both embed paths verify `SetParent` actually took (`SetParent` returning zero is ambiguous — a top-level window's previous parent is also zero, so success is confirmed via `GetParent`) instead of falling through claiming success (which left a hidden, parentless window = blank panel). The conhost path re-checks `IsWindow(terminalHandle)` + `HasTerminalProcessExited(cmdProcess)` before each `SetParent` so a window that died mid-embed (mode B above, Win32 1400) is detected at once and deferred to the outer relaunch rather than burning 3×200ms retrying against a corpse; a genuine embed failure also defers to the relaunch loop, and only the final post-loop failure reports via MessageBox + launch log. `EnsureTerminalPanelReady()` recreates `terminalPanel` and re-hosts it in `TerminalHost` when it is missing/disposed — previously a dead panel made the launch silently bail, and since the dead panel persisted, *every* later restart stayed blank until the project was reopened (the only failure mode matching that exact symptom)
- Teardown wait — all providers (issue #73; WSL-only in 10.98, extended in 11.0): after killing the process trees, `StopExistingTerminalAsync` polls the killed PIDs for up to 3s until they actually exit ("waited Nms for terminal teardown" in the launch log). Spawning the next terminal while the old session is still dying is what makes the fresh conhost exit instantly with code 0 or lose its window mid-embed — first reproduced with WSL teardown, but a reporter's log showed the same fingerprint with native Claude Code (slow claude/node tree teardown, e.g. corporate EDR), which is why the wait is no longer WSL-gated. Three supporting pieces (11.0): `KillProcessAndChildren` records every PID it kills into the caller's set (`Process.Kill` only *initiates* termination, and the old set held only tree roots — a lingering grandchild like the agent's node process let the wait pass early); the per-launch `_pendingTeardownProcessIds` set carries those PIDs into the relaunch loop, which holds each respawn up to 5s more while any are alive (an instant-exit attempt leaves nothing of its own to wait on, so without this the ladder kept respawning into the same dying tree); and the "conhost exited immediately" log line appends `oldSessionProcsAlive=N` so a user log alone confirms or rules out teardown contention
- Legacy console mode detection (issue #104, v63.0): `HKCU\Console\ForceV2 = 0` (the Windows 10 "Use legacy console" tweak) makes conhost create a pre-ConPTY console that rejects the embed handshake, so every launch fails immediately with `exitCode=-2147024809` (`0x80070057`, `E_INVALIDARG`) and the panel is permanently blank — 100% reproducible, never intermittent, which distinguishes it from the transient issue #73 modes above. It survives Windows 10 → 11 in-place upgrades because those preserve `HKCU`. The conhost branch of `StartEmbeddedTerminalAsync` calls `HandleLegacyConsoleModeAsync()` before spawning: `IsLegacyConsoleForced()` (absent value = modern V2, the Win11 default) → prompt → `TryEnableV2Console()` writes `ForceV2 = 1` (HKCU, so no elevation) → offer `IVsShell4.Restart(RESTART_Normal)`. Declining sets `_legacyConsoleFixDeclined` so the prompt doesn't repeat every relaunch in the session, and the post-relaunch-loop failure MessageBox re-checks `IsLegacyConsoleForced()` to name the cause and print the manual `reg add` instead of the generic "report it with the log" text. Not checked on the WT path (Windows Terminal doesn't create a legacy console)
- WT embedding: Finds `CASCADIA_HOSTING_WINDOW_CLASS`, embeds with `WS_CHILD`, calculates tab bar height offset; the WT path logs to the launch log like the conhost path (spawn PID, window-not-found, SetParent failures)
- Terminal hidden from taskbar: `WS_EX_TOOLWINDOW` + clear `WS_EX_APPWINDOW`
- F5 forwarding: Low-level keyboard hook (`WH_KEYBOARD_LL`) intercepts F5/Ctrl+F5/Shift+F5 → VS debug commands via DTE
- Mouse hook (`WH_MOUSE_LL`): Applies Ctrl+Scroll zoom (persisted into the console font size setting for Command Prompt since v78.0, live-only for Windows Terminal — see the conhost zoom paragraph below); converts plain left-drag to SHIFT+drag for WT text selection. WT selection assist must run inline on the hook thread, not marshaled (issue #99, v53.0): `BeginWindowsTerminalSelectionTracking`/`UpdateWindowsTerminalSelectionTracking`/`ResetWindowsTerminalSelectionTracking` used to run on the UI thread via the same `Dispatcher.BeginInvoke` fire-and-forget marshal as the rest of `HandleMouseHookEvent`. Windows Terminal (and the app's own VT mouse tracking underneath it) decides per mouse message whether SHIFT is down at the moment it arrives to choose between local text selection and forwarding the drag to the app — so any queuing delay before the injected `keybd_event(VK_SHIFT)` lands (arbitrarily long whenever the VS UI thread is busy, the exact scenario `_hookThread` from issue #61 exists to route around) meant the app frequently already owned the drag by the time SHIFT arrived, silently breaking selection/copy. Fixed by calling these three directly from `LowLevelMouseHookCallback` for `WM_LBUTTONDOWN`/`WM_MOUSEMOVE`/`WM_LBUTTONUP`, synchronously on the hook thread; the hit test moved to `IsScreenPointInsideTerminalWindow` (plain `GetWindowRect(terminalHandle, …)`, no WPF/WinForms — mirrors `TryForwardConhostCtrlZoom`'s pattern) since the WinForms-touching `IsScreenPointInsideActiveTerminalPanel` isn't safe off the UI thread. `WM_MOUSEMOVE`/`WM_LBUTTONUP` are no longer marshaled to the UI thread at all (`ShouldDispatchMouseHookMessage` only forwards `WM_LBUTTONDOWN`, still needed there for `ActivateEmbeddedTerminalOnClick`); the selection-tracking bookkeeping fields (`_windowsTerminalSelectionPending`/`_windowsTerminalSelectionActive`/`_windowsTerminalSelectionModifierInjected`/`_windowsTerminalSelectionStartPoint`) are now touched exclusively from the single hook thread. WT copy matches Command Prompt: drag to select, right-click to copy (issue #99 follow-up, same v53.0): fixing the timing race made SHIFT-drag reliably highlight text, but a reporter came back twice more — first that there was no way to copy a highlight at all, then (after an interim fix auto-copied on mouse-up via an injected Ctrl+Shift+C) that copying *and clearing* the selection the instant the mouse button was released was "strange" and didn't match Command Prompt's model of drag-to-select-and-keep-it-highlighted, right-click-to-copy-and-clear. `ResetWindowsTerminalSelectionTracking` (`WM_LBUTTONUP`) now only releases the injected SHIFT, if any — it no longer sends any copy keystroke, so a selection survives past mouse-up exactly like conhost. Copy-on-right-click is delegated entirely to Windows Terminal's own global `rightClickAction` setting rather than reintroduced as a hook-based right-click interceptor (which is exactly the design issue #90 already ruled out, see below): `EnsureWindowsTerminalRightClickCopyPaste()` patches WT's `settings.json` to set `"rightClickAction": "copyPaste"` once (mirrors `EnsureWindowsTerminalFontProfile`'s parse/mutate-if-different/write pattern, called unconditionally on every WT launch, cheap no-op once already set) — WT then natively copies-and-clears an active selection on right-click, or pastes when there's no selection, with no extension-side keystroke injection or right-click hooking at all. Conhost Ctrl+Scroll zoom is input-mode-independent (issue #76/#78): for the Command Prompt terminal (`_wtTabBarHeight == 0`), `TryForwardConhostCtrlZoom` runs on the hook thread (Win32 `GetWindowRect` hit test, no WPF/WinForms), consumes the physical wheel (returns 1), and changes the console font size directly via `SetCurrentConsoleFontEx` (`TryAdjustConhostFontSize`), then schedules the repaint on the UI thread. The size the zoom settles on is persisted (v78.0): once the drain worker has emptied the notch accumulator it converts the resulting cell height back to points (`ConsoleCellHeightPxToFontPt`, the exact inverse of the `ConsoleFontPtToCellHeightPx` used when writing the launch-time registry value, clamped to the 6–36 pt the Settings combo offers) and writes it to `ConsoleFontSizePt` via `PersistConhostZoomFontSize` + `SaveSettings`, so the next session opens at that size with no trip to Settings. Persisting after the drain (not per notch) keeps a fast scroll from rewriting the settings file dozens of times. Deliberately conhost-only: Windows Terminal handles Ctrl+Scroll internally and the gesture never reaches the extension, so there is no size to capture there. This is not a revival of the v73.0 auto-zoom replay — nothing replays a *delta* at startup; the terminal simply launches at a normal configured font size. `PersistConhostZoomFontSize` omits the usual `ThrowIfNotOnUIThread` guard on purpose: it would mark the method UI-thread-only for the analyzer, which then propagates the requirement up through the drain worker to the mouse-hook callback that legitimately runs off-thread. Notches are coalesced (v73.0, fixes occasional freeze/runaway on fast scroll): instead of spawning a `Task.Run` font-change per wheel notch, each notch does `Interlocked.Add(ref _pendingConhostZoomSteps, ±1)` and ensures a single drain worker (`_conhostZoomWorkerActive` 0/1 flag, `StartConhostZoomDrainWorker`) is running. The worker `Exchange`s the accumulated total, applies it in one `TryAdjustConhostFontSize(steps)` call, waits ~25 ms for more notches to accumulate, then re-checks and loops; it releases the flag and re-acquires via `CompareExchange` so a notch landing in the gap is never stranded. This matters because each `TryAdjustConhostFontSize` does an `AttachConsole`/`FreeConsole` under `_consoleSnapshotLock` and every attach briefly bounces the conhost's keyboard focus — one attach per fast-scroll burst instead of N stops the focus churn that made the zoom freeze/run away. `TryAdjustConhostFontSize` returns the signed notches actually applied (fewer than requested at the min/max clamp bound, 0 on no-change/failure) so the drain worker's loop bookkeeping stays exact at the clamp bound. The earlier v19 approach of posting `WM_MOUSEWHEEL + MK_CONTROL` to the conhost window did not work once a TUI put the console into mouse-input mode (QuickEdit off): conhost forwards both the physical wheel and a posted wheel to the app as input records, so neither reaches conhost's own zoom — that's why zoom worked only before the agent's TUI came up. Setting the font is independent of console input mode, so it works whether the TUI is up or not. WT is left on its native path (dispatch → `HandleMouseHookEvent`, which now only repaints the embedded panel after WT's native wheel zoom). Right-click is no longer intercepted at all (v29.0, root-fix for issue #90): the hook does not touch `WM_RBUTTONDOWN`/`WM_RBUTTONUP` — conhost/Windows handle the right mouse button natively everywhere (context menus in the editor/Solution Explorer, conhost's own QuickEdit-on right-click paste). The earlier "conhost right-click paste fallback" (issues #78/#82/#83) consumed right-clicks via a global `WH_MOUSE_LL` hook to paste into the agent's TUI when QuickEdit was off; despite an occlusion-aware + foreground-gated hit test it kept mis-firing — a right-click elsewhere in VS would be swallowed and the clipboard pushed into the console (issue #90) — so the whole feature was removed (`TryConhostRightClickPaste`, `IsScreenPointOverTerminalWindow`, `_consumeNextRButtonUp`, `_conhostInMouseInputMode` cache + `QueueConhostMouseInputModeRefresh`, and the `WM_RBUTTONDOWN/UP` constants are all gone). Pasting into the agent goes through the prompt box, whose send path delivers via `PasteViaConhostPasteCommandAsync` (conhost's own Edit→Paste `WM_COMMAND/ID_CONSOLE_PASTE` posted straight to `terminalHandle`) regardless of QuickEdit/mouse-input mode — so no terminal right-click paste is needed. `PasteViaConhostPasteCommandAsync` and `IsTerminalInMouseInputMode()` remain, now used only by the send path (the mouse-input-mode probe still drives whether the send path injects its pre-deselect right-click). TUI Fullscreen removed, Claude Code always launches classic (v53.0): the model-menu "TUI Fullscreen" toggle (`TuiFullscreenEnableMenuItem`/`TuiFullscreenDisableMenuItem`, `SendTuiModeCommandAsync`, `ClaudeCodeSettings.ClaudeTuiFullscreen`) is gone — `GetClaudeCommand()` now unconditionally prefixes the launch with `CLAUDE_CODE_DISABLE_ALTERNATE_SCREEN=1` instead of branching on a persisted tri-state setting. This also retired the issue #96 fullscreen-only mouse-wheel-to-PgUp/PgDn forwarding (`IsClaudeFullscreenConhostActive`, `GetFullscreenWheelScrollKeystrokeCount`, `SendScrollKeyToTerminal`, `TryEnsureFullscreenLineScrollKeybinding`/`AddBindingIfAbsent` and the `keybindings.json` line-scroll installer) since fullscreen (alternate-screen) rendering can no longer be entered through the extension, making that whole path permanently unreachable; `ShouldDispatchMouseHookMessage`'s `WM_MOUSEWHEEL` case now dispatches only for Ctrl held, and `HandleMouseHookEvent`'s wheel branch lost its plain-wheel-forward `else if`. Ctrl+Scroll zoom hijacked other apps when VS wasn't foreground (v51.0): both zoom paths — `TryForwardConhostCtrlZoom` (conhost) and the `ctrlDown` branch of `HandleMouseHookEvent` (Windows Terminal) — only hit-tested the cursor against the terminal's screen rectangle, which stays valid even when another maximized window is now layered on top of that same screen region (VS backgrounded). Global `WH_MOUSE_LL` doesn't know z-order, so Ctrl+Scroll in that other app got silently redirected into zooming the (invisible) embedded terminal instead of reaching the app the user was actually looking at. Fixed by extracting `IsTerminalHostForeground()` (the `GetForegroundWindow() == terminalHandle || hostRoot` check, previously inlined at the top of `IsTerminalFocused()`) and requiring it in both zoom paths before the rect hit test runs — cheap enough for the hook thread (same GetForegroundWindow-based short-circuit `IsTerminalFocused()` already relied on). Deliberately stops short of requiring full `IsTerminalFocused()` (keyboard focus on the terminal control specifically) so hover-to-zoom while VS is foreground still works without first clicking into the terminal.
- Classic-mode mouse tracking disabled unconditionally (v112.0, issues #118/#119): `GetClaudeCommand()`'s always-classic launch prefix (`CLAUDE_CODE_DISABLE_ALTERNATE_SCREEN=1`, v53.0 above) now always adds `CLAUDE_CODE_DISABLE_MOUSE=1` too, for both the cmd.exe and WSL command-prefix forms. Current Claude Code CLI builds turn on terminal mouse tracking (conhost QuickEdit disabled / `ENABLE_MOUSE_INPUT`) even in the classic renderer — confirmed by `IsTerminalInMouseInputMode()` (the paste path's probe) detecting QuickEdit-off sessions with no fullscreen involved. With mouse tracking on, conhost forwards the physical wheel to Claude's stdin as mouse-report escape sequences instead of scrolling its own buffer, so the wheel did nothing while the agent was generating (#118, "can't scroll up to see earlier output") and, on long/busy sessions, likely fed the fast-input heuristic stray escape data that rendered as garbled/overlapping text (#119). Same fix already proven for fullscreen under issue #92 (above) — now unconditional since fullscreen no longer exists to gate it on.
- Windows Terminal runaway-zoom guard (v94.0, issue #117): unlike the conhost path — where `TryAdjustConhostFontSize` hard-clamps the cell height — WT owns its Ctrl+Scroll zoom entirely and has no ceiling, so nothing bounded it. Reporters described the font "progressively growing till it is huge" shortly after load and self-resolving later, the fingerprint of a notch burst (real or spuriously synthesized) arriving far faster than a human could scroll. There is no simple API to read or reset WT's own zoom level, so `IsRunawayWtZoomBurst` instead counts Ctrl+wheel notches over the terminal in a rolling window (`WtZoomBurstWindowMs` 1500 / `WtZoomBurstMaxNotches` 30) and, once the burst clears that generous ceiling, `LowLevelMouseHookCallback` returns 1 to swallow the notch before WT ever sees it — bounding the damage regardless of what triggered the burst. Gated on `_wtTabBarHeight > 0` (WT only), `IsTerminalHostForeground()` and the `GetWindowRect` hit test, the same trio the zoom paths already use; the counters are `Volatile`/`Interlocked` because this runs on the hook thread
- Post-startup: `SchedulePostStartupTerminalAdjustments()` runs the deferred layout stabilization (`StabilizeEmbeddedTerminalLayoutAsync`); `SchedulePostSolutionLoadTerminalRefresh()` does 200/500/1000ms repaint passes after solution load. The startup auto-zoom was removed in v73.0 — it used to replay a saved `TerminalZoomDelta` and apply a default WT zoom-out a beat after embedding, but that conflicted with the new console font size setting and was the root cause of the "no keyboard input at the start of the session" bug: the console-attach font change / synthesized Ctrl+- keystrokes it fired bounced the shared native keyboard focus onto the just-embedded terminal, leaving the prompt dead until the user clicked it twice. Startup now just focuses the prompt AND arms `EnsureWpfPromptFocusGuardRunning()` as belt-and-suspenders — the guard re-asserts prompt focus for ~0.7s but only while the terminal is the one holding it, and aborts the instant the user clicks the terminal, so it never fights a user who wants to type in the terminal.
- Fresh PATH from registry: `GetFreshPathFromRegistry()` reads PATH from `HKLM` and `HKCU` registry keys to detect newly installed tools (e.g. Windows Terminal) without requiring VS restart
- Codex terminal resume from Session History (v132.0): `GetCodexCommand()` consumes `_pendingResumeSessionId` after model/reasoning/approval global flags are assembled and appends `resume <id>` (or `resume --last` for the internal continue sentinel), quoting the id for cmd.exe vs Bash. The approval-never branch must append its flag instead of returning early, otherwise history silently opens a fresh thread whenever that option is enabled
- WPF keyboard-focus reclaim (issue #65): `SetParent`ing the terminal (separate-process window) into VS joins that process's input queue with the VS UI thread, so keyboard focus is shared state. If it gets stuck on the terminal, WPF's `Focus()` won't always move native focus back — the prompt stops accepting typing (caret stops blinking) and the provider menu can't be arrow-navigated until VS restarts. `ClaudeCodeControl_PreviewMouseLeftButtonDown` (tunneling, fires before any child handles the click) calls `ReclaimWpfKeyboardFocusIfStuck()`: when `GetFocus() != HwndSource.Handle` it `SetFocus`es the WPF host, so one click anywhere restores typing. No-op when WPF already owns focus
- Terminal-click activation (issue #69): a click on the embedded terminal runs `ActivateEmbeddedTerminalOnClick` (from the mouse hook), which raises the VS top-level window (`BringVisualStudioToForegroundIfNeeded`, AttachThreadInput dance to bypass focus-stealing protection) and selects the terminal pane (`IVsWindowFrame.Show()` when `IsTerminalToolWindowActive()` is false). Do not re-attempt a "don't bring VS to the foreground on terminal click" opt-out — it shipped in 10.82–10.90 and was removed in 10.91 as infeasible: keyboard input only goes to the foreground thread's focus window, so VS *must* be activated for typing to reach the terminal, and suppression attempts (`MA_NOACTIVATE` from the host panel, `WS_EX_NOACTIVATE` on the terminal — inert on `WS_CHILD` windows, gating `frame.Show()` via `ShowNoActivate()`) either didn't engage or would have broken typing. Windows itself also activates/raises the top-level owner when the cross-process child is clicked, outside the extension's control.
- WPF-prompt focus guard (v27.0, symmetric with the terminal guard): clicking the WPF prompt previously got only a single-shot `ReclaimWpfKeyboardFocusIfStuck()`, so a deferred steal (the cross-process terminal grabbing the shared native focus, or the OAF console attach on Command Prompt) landed a moment later and typing into the prompt went nowhere until the user clicked again. A self-extending guard now runs: `EnsureWpfPromptFocusGuardRunning()` (called from `ClaudeCodeControl_PreviewMouseLeftButtonDown` and `PromptTextBox_PreviewKeyDown`) refreshes `_lastPromptInteractionUtc` and, via `RunWpfPromptFocusGuardAsync`, re-asserts focus every 80ms until ~2s after the last prompt interaction (so it holds through active typing during generation, not just after one click). Single loop at a time (`_promptFocusGuardRunning`). It re-asserts only when the terminal specifically holds native focus (`GetFocus()` is the terminal or its child) — a WPF ContextMenu/Popup (the ⚙ menu) or child editor is left alone so menu/arrow nav isn't broken. Aborts on a terminal click (`_promptFocusGuardSeq`, bumped in `ActivateEmbeddedTerminalOnClick`) or an app switch, so the two guards never fight. v28.0 de-escalation: this guard window was cut to ~0.7s (`idleWindowMs`) and the terminal click guard to ~0.6s (`totalChecks = 8`). v27 had stretched the terminal guard to ~5s (to outlast the OAF console-attach focus bounce); with `FocusTerminalWindow` no longer merging an unrelated foreground thread's input queue (see below) the long windows were both unnecessary and harmful — they kept re-asserting focus for seconds and ping-ponged it between the terminal and the prompt, dropping keyboard/mouse input in the terminal while the agent was busy
- Single-click terminal focus (issue #74): the click natively focuses the terminal child, but both activation steps above make VS move keyboard focus into the WPF tool-window content moments later (`frame.Show()` focuses the pane content; `SetForegroundWindow` restores VS's last focused control) — so a click on the terminal could get its focus silently stolen before typing (e.g. answering an agent's choice prompt) reached it. The 10.94 fix re-asserted focus exactly twice at fixed +80/+160 ms — under heavy load (agent crunching, VS repainting) VS's restore landed *after* both asserts, so every click lost the race and the terminal became impossible to select (the issue's follow-up report). Since 11.0, `ActivateEmbeddedTerminalOnClick` always schedules `EnsureTerminalFocusAfterClickAsync`: 80 ms checks that re-assert via `FocusTerminalPanel` whenever `GetFocus()` isn't the terminal (or a child of it). It aborts when a newer click occurs anywhere (`_terminalClickSequence`, bumped per WM_LBUTTONDOWN in the mouse hook), when the foreground window leaves the VS root, or when the terminal/panel dies — so it can't fight the user, only VS's deferred restores. Focus state is read via `IsTerminalFocused()` (GetGUIThreadInfo, same check the F5 hook uses); ordinary clicks cost one such check per tick, no asserts. Self-extending guard (v46.0): the guard runs a `baseChecks`=20 (~1.6 s) window and then keeps going only while the user is *actively typing into the terminal* (`_lastTerminalKeyUtc` within `typingExtendMs`=700 ms), hard-capped at `absoluteMaxChecks`=100 (~8 s). This fixed the "can't type when the AI asks a question" hang: v28 had cut this to a fixed ~0.6 s (`totalChecks = 8`), so a VS focus-restore (or a pause before answering) landing after that short window stranded the terminal without focus and the reply went nowhere. Because it aborts on *any* click elsewhere (every left-click bumps `_terminalClickSequence` via the global mouse hook) and only self-extends while terminal keystrokes are actually arriving, it can't reintroduce the v26/v27 idle ping-pong (that came from the old ~5 s *unconditional* window plus the foreground-thread `AttachThreadInput` that no longer runs). `FocusTerminalWindow` (v28.0): SetFocus only, no foreground-thread `AttachThreadInput`. `SetParent` already joined the terminal thread's queue to VS, so a plain `SetFocus(terminalHandle)` moves native focus; only when that doesn't take does it briefly attach the *terminal* thread (already joined, so safe) and retry. v26/v27 also attached the current *foreground* thread's input queue on every focus set — merging an arbitrary busy thread into VS's synchronous input queue, which backed up all keyboard/mouse input while the conhost thread was rendering agent output (the reported "input freezes while the agent works, recovers when idle"). The F5 keyboard hook tracks `_lastTerminalKeyUtc` on every terminal keystroke (v46.0) so the self-extending click guard (and the OAF typing guard) know when the user is typing an answer into the terminal. This reverses the v28 `needFocus` gate that only computed `IsTerminalFocused()` for F5 or while a completion watch was active — with OAF off, terminal typing went untracked, which is why the answer-the-agent hang persisted without OAF. It stays cheap because `IsTerminalFocused()` short-circuits on `GetForegroundWindow` (the cross-process `GetGUIThreadInfo` runs only when a VS window is foreground, i.e. at human keyboard rates). `StartHookThread()` is also re-invoked on every terminal launch (idempotent) so a dead hook thread — which silently disables click activation and F5 forwarding — revives on the next start. The hit-test also accepts child windows of the terminal (`IsChild`), not just the exact handle.

- Focus-guard assert caps + terminal-busy notice (v59.0, issue #89): both focus guards now stop after 4 consecutive asserts that did not take (`consecutiveFailedAsserts` in `EnsureTerminalFocusAfterClickAsync`, `consecutiveFailedReclaims` in `RunWpfPromptFocusGuardAsync`; give-ups logged to terminal-launch.log). Every assert costs the terminal a native focus kill/set pair, which conhost forwards to the agent's stdin as FOCUS_EVENT input records — and the agent's TUI re-renders on those. With a very long turn on screen (a big plan) each re-render is expensive (the Windows CLI input-loop starvation of anthropics/claude-code#63504), so a guard hammering 80ms asserts for up to 8s actively fed the "keyboard locked when the agent asks a question" state it was meant to prevent. Click-guard retries after the first assert also use the lighter `FocusTerminalWindow()` (single SetFocus) instead of the full `FocusTerminalPanel()` dance (panel.Focus() + SetFocus = double the focus events). On give-up the click guard probes `IsTerminalWindowResponsive()` (`SendMessageTimeout(WM_NULL, SMTO_ABORTIFHUNG, 250ms)` — a saturated conhost stops pumping messages: clicks select nothing, SetFocus doesn't take, Esc falls through to VS tab navigation) and, when the conhost is genuinely hung, shows a once-per-minute info bar (`NotifyTerminalBusyCatchingUp`) telling the user the terminal is catching up and input will recover on its own. Root cause context: measured standalone (no VS/extension), the Claude Code CLI's classic renderer freezes its *menu* input for 60–90s after a ~1500-line output while plain typing echo stays at ~30ms — the lock is CLI-side; the extension work removes the extension's amplification and explains the episode instead of looking broken
- TUI fullscreen env vars (v31/v32, `GetClaudeCommand`): `_settings.ClaudeTuiFullscreen` (nullable) injects an env prefix ahead of the `claude` command — `true` → `CLAUDE_CODE_NO_FLICKER=1` plus `CLAUDE_CODE_DISABLE_MOUSE=1`; `false` → `CLAUDE_CODE_DISABLE_ALTERNATE_SCREEN=1` (classic renderer); `null` → nothing (CLI default). cmd.exe form is `set X=1 && set Y=1 && {cmd}`, WSL bash form is `X=1 Y=1 {cmd}`. `CLAUDE_CODE_DISABLE_MOUSE` is mandatory whenever fullscreen is on (issue #92): fullscreen rendering enables Claude Code's own terminal mouse tracking, which in the embedded conhost — where the extension already runs a global mouse hook and re-asserts focus — emits a continuous burst of mouse-input escape sequences that Claude's fast-input heuristic collapses into `[Pasted text +N lines]` bracketed-paste blocks, flooding the prompt on launch and on every restart. The extension supplies its own mouse zoom / click-to-focus / paste, so disabling Claude's mouse capture loses nothing while keeping the flicker-free draw. The one casualty is wheel scrolling: with Claude's mouse off, the wheel no longer pages the conversation (per Claude's docs, fullscreen + `DISABLE_MOUSE` keeps only the keyboard scroll keys `PgUp`/`PgDn`/`Ctrl+Home`/`Ctrl+End`, plus native terminal selection of the visible viewport). Wheel scroll restored without re-enabling Claude's mouse (v36, issue #96): the global mouse hook's `HandleMouseHookEvent` now, on a plain (no-Ctrl) wheel notch over the active panel when `IsClaudeFullscreenConhostActive()`, posts `VK_PRIOR`/`VK_NEXT` (PgUp/PgDn) keystrokes to the terminal via `SendScrollKeyToTerminal`. Two gotchas: (1) `ShouldDispatchMouseHookMessage` must let the plain wheel through — it otherwise forwards `WM_MOUSEWHEEL` only when Ctrl is held (zoom), so the plain-wheel case is gated on `IsClaudeFullscreenConhostActive()` there too, or the handler never runs. (2) `SendScrollKeyToTerminal` builds a real `lParam` (scan code from `MapVirtualKey` + extended-key bit) — conhost silently drops a posted key with a zero scan code instead of translating it to VT input (`ESC[5~`/`ESC[6~`). Posted straight to `terminalHandle` (focus-independent, like the Enter path); gated to conhost (`_wtTabBarHeight <= 0`) and the Claude Code / Claude Code (WSL) providers so it never hijacks conhost's own scrollback in the classic renderer or Windows Terminal's native wheel handling. Smooth line scroll (vs. the half-page PgUp default): for *native* Claude Code, `TryEnsureFullscreenLineScrollKeybinding()` merges `pageup`→`scroll:lineUp`, `pagedown`→`scroll:lineDown` (and `shift+pageup/pagedown`→`scroll:halfPage*` to preserve paging) into `%USERPROFILE%\.claude\keybindings.json` — those line-scroll actions are unbound by default, so the wheel had nothing finer than half-page to trigger. With the binding in place each notch sends one PgUp/PgDn (`GetFullscreenWheelScrollKeystrokeCount()` returns 1) for a one-line step; WSL Claude (config lives in the WSL filesystem) and any write failure fall back to a single half-page keystroke. The keybinding file is touched once per session, lazily on first wheel scroll, and merges without overwriting existing user bindings (`AddBindingIfAbsent`).

Launch command routed through a temp script, not embedded in the outer argument string (issue #106): both embed paths hand the `/k ...` command line to an intermediate process — `wt.exe` or `conhost.exe` — as a `ProcessStartInfo.Arguments` string, and that intermediate re-parses/re-tokenizes the whole string before it reaches `cmd.exe`. A workspace path containing `" - "` (e.g. a solution folder named `MS-059 - ZZZZ-EC16`) could come out of that re-parse with stray quotes injected around the dash, corrupting `cd /d` and failing the launch with `ERROR_FILE_NOT_FOUND`. `WriteLaunchScript()` (in `StartEmbeddedTerminalAsync`) strips the leading `/k ` and writes the rest of the command chain, verbatim, to a `launch_{guid}.cmd` file under the control's own `ClaudeCodeVS_Session` temp folder (`tempImageDirectory` — already cleaned up on startup, see Cleanup.cs); the outer Arguments then become the short, dash/space-free `--window new {fontProfileArg}-- cmd.exe /k call "{scriptPath}"` (WT) or `-- cmd.exe /k call "{scriptPath}"` (conhost). `call` (rather than relying on `/k`'s own quote-stripping of a bare quoted path) makes the batch-file invocation unambiguous; running via `call` from an interactive `/k` session keeps `cd`/env changes in the same process, so behavior (cwd, foreground app inheriting the console) is unchanged from the inline form. This keeps the fragile workspace path out of every argument string an intermediate process tokenizes — only the script's own GUID-named path has to survive it.

Command patterns (now the body of the temp script `WriteLaunchScript()` writes, not the literal `Arguments` string):
```
Windows: chcp 65001 >nul && cd /d "{dir}" && ping localhost -n 3 >nul && cls && {command}
WSL:     chcp 65001 >nul && cls && wsl bash -lic "cd {wslPath} && {command}"
```

Console font / codepage registry (`SaveAndSetConsoleFontRegistry` / `RestoreConsoleFontRegistry`): conhost reads `HKCU\Console` once when a console window is created, so the font (`FaceName` + `FontFamily=54` TrueType) is written before spawning conhost and restored after it has started. `FaceName` comes from `_settings.ConsoleFontFaceName` (Settings → Terminal; default `"Cascadia Mono"`, empty falls back to it) so users on CJK/non-Latin systems can pick a font that renders their script — Cascadia Mono has no Han/Kana/Hangul glyphs, so without this they relied on conhost's font fallback. Font size (`_settings.ConsoleFontSizePt`, Settings → Terminal; `0` = leave conhost's default) is written to the `FontSize` DWORD as `(heightPx << 16)` — the point size is converted to a pixel cell height (`px = pt·96/72`), width left 0 so conhost derives it for TrueType. `FontSize` is only touched when a size is configured (`_consoleFontSizeSaved` gates the restore), so users who never set one keep conhost's default sizing. Changing the font or size relaunches the terminal. `CodePage=65001` is written to the per-executable subkey `Console\%SystemRoot%_System32_conhost.exe` (the parent `Console\CodePage` is ignored by conhost in practice); the original values are saved and the subkey is deleted on restore if we created it.

Console font under Windows Terminal (`EnsureWindowsTerminalFontProfile` / `GetWindowsTerminalFontProfileArg`): WT ignores `HKCU\Console` and `wt.exe` has no font flag, so the only lever is `settings.json`. The `ConsoleFontFaceName` + `ConsoleFontSizePt` settings drive a dedicated managed profile ("Claude Code Extension", fixed GUID `{b9a3c7e2-…}`) carrying `font.face` and (when a size is set) `font.size` in points; the launch passes `-p "Claude Code Extension"` (the trailing `-- cmd.exe {cmd}` still overrides the profile's command line). The profile inherits colors/cursor/etc. from `profiles.defaults`. Blast radius is kept minimal: `settings.json` is touched only when a non-default font face OR a non-default size is selected (default face `"Cascadia Mono"`/blank *and* size `0` → no `-p`, untouched file) and only when the profile is missing or its face/size differs; when only a size is set the profile still carries a valid monospaced face (falls back to Cascadia Mono), and clearing the size removes `font.size`. Handles both schemas (`profiles.list` array and legacy bare `profiles` array). Caveat: rewriting via Newtonsoft serialization drops the user's `//` comments — accepted because writes are rare and gated to non-default font settings. Any failure (no settings.json, parse/write error) returns null and the launch falls back to WT's default profile. The Settings picker (a searchable, live-preview ListBox of `Fonts.SystemFontFamilies`) plus the point-size combo are shared by both terminal types. The console font size is the persistent size control — Ctrl+Scroll zoom is live-only and no longer replayed on restart (v73.0), so the terminal always launches at exactly the picked size.

WSL path conversion (`ConvertToWslPath()`): `\\wsl.localhost\distro\path` → `/path`, `C:\...` → `/mnt/c/...`

WSL shell mode: Uses `bash -lic` (login + interactive) to load `.profile`/`.bash_profile` PATH entries — applies to all WSL providers (Claude Code WSL, Codex WSL, Cursor Agent WSL, Devin). WSL launch commands must go through `BuildWslLaunchCommand()` so the cwd is Bash-quoted before it is embedded in the outer `cmd.exe` command.

## Provider Detection (ProviderManagement.cs)

- Caching: `_providerCache` (5-min TTL), separate `_wslCache` for WSL install status; `_cacheLock` for synchronized access; `IsCacheValid()` checks expiry
- Claude Code detection: Two-tier — first checks native path (`%USERPROFILE%\.local\bin\claude.exe`), then falls back to `where claude` (PATHEXT-aware, finds both `claude.exe` from winget and `claude.cmd` from NPM)
- PATH refresh backfilled to the remaining `where`-based detectors (v113.0, issue #124): `GetFreshPathFromRegistry()` was already wired into the Antigravity/Reasonix/Devin-native checks (added alongside those newer providers) but never backported to the CLIs that predate it — Claude, Codex (native), Cursor Agent (native), Open Code, PI all ran `where <tool>` against the process's inherited (and often stale) `PATH` only. Reported as Codex reporting "not installed" for a CLI that was in fact on `PATH`, working only once a custom CLI path was configured manually to bypass detection entirely — classic symptom of installing the CLI (or its PATH-modifying installer) after Visual Studio was already running, since `devenv.exe`'s environment block is a snapshot from launch and Windows does not push registry `PATH` edits into already-running processes. Now all five call `GetFreshPathFromRegistry()` and pass it as the child `where` process's `PATH` before checking, same as the other native detectors, so a CLI installed after VS started is found without a VS restart
- WSL detection: `bash -lc` (login shell) for `which` — avoids `.bashrc` noise; retries 2x with 8s/20s timeouts for cold boot
- PI detection: `IsPiAvailableAsync()` runs `cmd /c where pi` (3s timeout), available when exit code 0 and stdout non-empty; native Windows NPM tool (`@earendil-works/pi-coding-agent`), TUI — paste uses Shift+Right-click and `WM_CHAR` Enter like Open Code
- Antigravity detection: `IsAntigravityAvailableAsync()` runs `cmd /c where agy` (3s timeout, PATH refreshed from registry), available when exit code 0 and stdout non-empty; Google's native Windows agent (install `irm https://antigravity.google/cli/install.ps1 | iex` to `%LocalAppData%\agy`, launched with `agy`). Runs in conhost, `WM_CHAR` Enter like Claude Code. Paste workaround: Antigravity disables conhost `ENABLE_QUICK_EDIT_MODE` at startup (re-disables faster than `SetConsoleMode` can restore), so a plain right-click opens the context menu instead of pasting. Dedicated paste branch right-clicks to open the menu, then Down ×3 → Enter via `keybd_event` to land on Paste (menu order Mark/Copy[disabled]/Paste/…; arrow nav stops on disabled items; locale-agnostic). Delays generous (500ms after right-click, 150ms between keys) — rushing drops keys. Excluded from the `isCommandPrompt` cancel-selection right-click
- Reasonix detection: `IsReasonixAvailableAsync()` runs `cmd /c where reasonix` (3s timeout, PATH refreshed from registry), available when exit code 0 and stdout non-empty. DeepSeek-native coding-agent TUI installed via `npm i -g reasonix` (so it lands on PATH); native Windows conhost, modeled on Antigravity/PI. Launched with plain `reasonix` (no flags, no model arg — minimal scope). Paste uses the shared `WM_COMMAND` conhost paste; Enter is a single `WM_CHAR` like PI/Open Code; exit/update interrupts the TUI with CTRL+C then runs `npm i -g reasonix`. DeepSeek API key (`DEEPSEEK_API_KEY`) is the user's own concern. Optional CLI-path override supported but not required
- Devin (native) detection: `IsDevinNativeAvailableAsync()` runs `cmd /c where devin` (3s timeout, PATH refreshed from registry), available when exit code 0 and stdout non-empty. Native Windows port of the same `devin` CLI as Devin (WSL); install must be done from Windows Terminal (`irm https://static.devin.ai/cli/setup.ps1 | iex`) but the resulting `devin` runs in both Windows Terminal and conhost. Launched with plain `devin` (no flags). Because it is the same `devin` TUI as Devin, it shares the configurable model list (`_settings.DevinModels`) and the Devin model menu (`ModelContextMenu_Opened` treats `DevinNative` like `Devin`); model switches send `/model "<name>"` (quoted) to the running terminal. Enter uses the KEYDOWN/KEYUP path (`SendEnterKeyDownUp`) like Devin, paste stays on the clipboard path (excluded from clipboard-free per-char keystrokes like PI/Reasonix), and exit sends `exit`; update force-kills lingering `devin.exe` then runs the official updater via PowerShell (`taskkill /f /im devin.exe >nul 2>&1 & powershell -NoProfile -ExecutionPolicy Bypass -Command "irm https://cli.devin.ai/install.ps1 | iex"`) because `devin update` does not update — it only prints the install command, and the installer's `Copy-Item` over `%LOCALAPPDATA%\devin\cli\bin\devin.exe` fails with "Access is denied" while any `devin.exe` is still running (self-update lock). Not a WSL provider (no path conversion). Optional CLI-path override supported
- Early-exit logic: Stops retrying only when stdout has content (ignores stderr-only warnings)
- Notification flags: Static booleans (one per provider) ensure install pop-ups show only once per VS session
- Active provider UI source (v24.0): provider checkmarks, provider-specific flag visibility, model/usage menu visibility, tool-window captions, detached captions, and visible-agent "active" labels use `GetActiveOrSelectedProvider()` — `_currentRunningProvider` when a terminal is alive, falling back to `_settings.SelectedProvider` only before launch. Successful launches sync `_settings.SelectedProvider` in memory, while `SaveSettings()` still preserves volatile provider/model/effort fields from disk during normal operation for multi-instance isolation.
- Model menus (generalized in v111.0): `ModelContextMenu_Opened()` shows Claude's fixed XAML items for Claude providers and, for every other agent, a list built at open time by `RebuildProviderModelMenuItems(provider)` — items inserted at the top of `ModelContextMenu` and tracked in `_dynamicDevinModelItems` for removal on the next open. The entries come from `GetCachedProviderModels` (the CLI catalog, or `_settings.DevinModels` / `_settings.ReasonixModels`), followed by "Refresh Models" for the CLIs that list their own models, "Configure Models..." for Reasonix, and "Choose in the Agent..." (`GetSimpleModelCommand`) as the escape hatch. Picking one records the selection (`SetSelectedProviderModelId`); Devin and Reasonix then switch live through `GetLiveModelSwitchCommand` (`/model "<name>"` and `/model <id>`), and every other agent takes its model at launch, so the handler offers a restart. See *Model Catalog & Selection*
- Devin model list is editable from two menus (v98.0): the same `ConfigureDevinModels()` body is reached from "Configure Models..." in the 🤖 model menu (`DevinConfigureModelsMenuItem_Click`) and from "Configure Devin Models..." in the ⚙ provider menu (`ConfigureDevinModelsProviderMenuItem_Click`), whose visibility `UpdateProviderSelection()` gates on `Devin`/`DevinNative` alongside the other provider flags. The second entry point exists because in native mode the 🤖 menu is not the composer's model picker, so the list was otherwise uneditable there. The seeded `DevinModels` defaults were refreshed in the same release (Claude Opus 5 High / Claude Sonnet 5 High first) — they are only a *seed*, so an existing user's saved list is untouched, which is exactly how a stale entry can outlive a CLI rename (see the `ResolveModelValue` note under *Native Mode*)
- No model shown as selected (v62.0): Claude and Devin model items are plain (not `IsCheckable`) and no checkmark is ever set, and the tool-window/detached captions are the bare provider name (`GetProviderDisplayName`) with no `" - <model>"` suffix. The CLI owns the active model — the user can change it with `/model` inside the terminal, and Claude Code also falls back between models on its own — so any selection the extension displayed was a guess that went stale. `SelectedClaudeModel`/`SelectedDevinModel` are still recorded on click (and `EnsureDevinModelDefaults()` still normalizes the Devin one against the configured list) but nothing reads them for display. Narrowed in v111.0: the agents whose model the extension itself passes at launch (`SelectedProviderModels` → `-m`/`--model`/env) *do* show a checkmark on the selected entry, because there the extension is the one that decided. Claude and Devin keep the old rule — their CLI owns the active model
- Simple model command (the agent's own picker): Codex/Cursor/PI/Antigravity/Reasonix use `/model`; Open Code uses `/models`. Until v111.0 this *replaced* the menu for those agents — `ModelDropdownButton_Click` sent the command instead of opening `ModelContextMenu`. It is now the last entry of the generalized menu ("Choose in the Agent...", `OpenAgentModelPickerMenuItem_Click`), enabled only when `_currentRunningProvider == activeProvider` (a matching terminal is live) since it is sent with `SendTextToTerminalAsync`. Button visibility (`RefreshToolbarLayout`) is gated on `IsClaudeProvider(...) || ProviderHasModelCatalog(...)`. Enter handling is Codex-specific. The other providers use the normal `SendEnterKey()` (a single-stage picker opens fine). Codex is sent with `SendTextToTerminalAsync(cmd, singleEnterEvent: true)`, which posts a lone `WM_KEYDOWN VK_RETURN` (no key-up) after the paste. Codex's `/model` picker is two-stage (model → effort) and its TUI reads raw key events (it ignores the translated `WM_CHAR`, so a `WM_CHAR '\r'` doesn't submit at all) and counts both the key-down and the key-up as an Enter — so a normal KEYDOWN/KEYUP pair is a *double* Enter that over-submits: measured behavior was 1 down/up → lands on effort (skips model), 2 → back to the prompt, `WM_CHAR` → nothing. A single key-down event submits `/model` once and leaves the picker on the model list
- Effort slider (v42.0, Claude only): the Claude effort picker is a pill `Slider` (6 stops) hosted in a `StaysOpenOnClick` `MenuItem` (`EffortSliderMenuItem`) inside `ModelContextMenu`, styled via `EffortSliderStyle`/`EffortFillButtonStyle`/`EffortThumbStyle` in `ClaudeCodeControl.xaml`. Mirrors the VS Code effort slider; the visual order (Low, Medium, High, XHigh, Max, Ultracode) is defined by `_effortSliderOrder` and is decoupled from the `EffortLevel` enum's integer values via `EffortFromSliderIndex`/`EffortToSliderIndex` — `XHigh`/`Ultracode` are appended after `Max` in the enum (so legacy persisted values `Auto=0..Max=4` stay stable) but reordered for display; legacy `Auto` falls back to the High stop. The fill is blue and turns purple at the top Ultracode stop via a `DataTrigger` on `Slider.Value == 5`. `/effort` sends the lowercased level name: `XHigh → /effort xhigh` (shown as "Extra High"), `Max → /effort max`, `Ultracode → /effort ultracode` (shown as "Ultracode - xhigh + workflows"; a single effort tier that combines xhigh effort with dynamic workflows, not two commands). `EffortSlider_ValueChanged` updates the caption live and commits via `SetEffortLevelAsync` — immediately for click/keyboard, deferred to `EffortSlider_DragCompleted` while dragging (`_effortSliderDragging`/`_pendingEffortLevel`). `UpdateEffortSelection()` syncs slider position from `_settings.SelectedEffortLevel` under `_suppressEffortSliderChange`; it's called on menu open, provider switch, and settings reload. Session-only levels (v43.0): `Max` and `Ultracode` are transient (mirrors the CLI, where `/effort max` is "this session only"). They apply live and `_settings.SelectedEffortLevel` reflects them during the session, but they are never persisted: `SetEffortLevelAsync` records the last durable pick in `_lastPersistableEffortLevel` (only when `!IsSessionOnlyEffort`), and `SaveSettings` substitutes that durable level for `SelectedEffortLevel` whenever the live value is session-only — important on shutdown, where volatile-field disk-preservation is skipped (`_isShuttingDown`) and the in-memory value would otherwise be written. `LoadSettings` seeds `_lastPersistableEffortLevel` from disk and normalizes any legacy-persisted `Max`/`Ultracode` back to `High`

- Native mode hides the console-only controls (v89.0): `RefreshToolbarLayout` computes `hasConsole = !IsNativeModeActive` and passes it as the constraint for UpdateAgent (its whole implementation is "exit the agent, then run the installer at the shell prompt" — it used to answer *"Terminal is not running. - Change Account in the `⚙` menu (v91.0, real `claude auth` calls in v112.0, WSL support in v113.0): the one 🤖-menu feature that got a real native implementation instead of being hidden. `ChangeAccountNativeMenuItem`/`ChangeAccountNativeSeparator` (own item, not the terminal's `ChangeAccountMenuItem`) are shown by `ProviderContextMenu_Opened` only when `IsNativeModeActive && IsClaudeProvider(...)`. `ChangeAccountNativeMenuItem_Click` (NativeChat.cs) can't script `/logout` into a TUI that doesn't exist headless — measured: the headless CLI rejects slash commands sent over the structured channel outright (`AskSideQuestionAsync`'s `/btw` comment: *"isn't available in this environment"*). The v91.0 fix opened `https://claude.ai` in the default browser and relied on the user switching there, but that never actually worked: a browser session against the web app is a completely separate credential store from the one the locally-run CLI authenticates with, so the relaunch always came back on the same cached account (issue reported as "switching doesn't work"). v112.0 replaces the browser-homepage step with the CLI's own non-interactive `claude auth logout` (awaited, clears the real local credential) followed by `claude auth login` (fire-and-forget — it drives its own OAuth round-trip in the browser and isn't killed by disposing the `Process` wrapper without `Kill()`). v112.0 shipped this unconditionally against `ResolveNativeClaudeExecutable()` (the Windows-side `claude.exe`) even for the `ClaudeCodeWSL` provider — but a native-mode `ClaudeCodeWSL` session's actual child process is `wsl.exe` (`ClaudeCommandBuilder.GetFileName`), authenticating against the distro's own `~/.claude.json`, a completely separate file from the Windows one. So the v112.0 handler logged out/in a Windows credential the running WSL conversation never used: no error, but the switch silently did nothing for WSL. v113.0 fixes this by branching on `isWsl = activeProvider == AiProvider.ClaudeCodeWSL` and running both subcommands as `wsl.exe bash -lic "claude auth logout"` / `"claude auth login"` instead. Still signs out the usage WebView2 first (`SignOutUsageWindowIfActiveAsync`, same as the terminal flow) and still waits for an OK on a message box before calling `RelaunchNativeSessionAsync` so the next turn's process launch picks up whatever credentials are current at that point. `auth login` needs a real console, unlike `auth logout` (also fixed v113.0): `claude auth login` drives an interactive OAuth round-trip — it prints the browser URL to stdout and, if the browser's own redirect can't complete automatically, asks the user to paste a code back into that same process's stdin. The original v112.0 `Process.Start` used `CreateNoWindow = true` for both subcommands; `auth logout` does no interactive I/O so that was harmless, but for `auth login` it meant the process had no console at all — no stdout to print the browser URL/prompt to, no stdin to read a pasted code from — so the browser never opened and login could never actually complete, even though the `Process.Start` call itself raised no exception (reported: "browser is not opening", "not showing new account after OK", "even a new chat doesn't show the account" — all three were downstream of this one root cause, since the account was never actually being set). Fixed by launching it through `cmd.exe /k` with `CreateNoWindow = false` (`cmd.exe /k "<claudeExe>" auth login`, or `cmd.exe /k wsl bash -lic "claude auth login"` for WSL) — the same `/k`-wrapped visible-console pattern the terminal launch itself uses elsewhere in `ClaudeCodeControl.Terminal.cs`, which gives the CLI a real window to print to and read from, and keeps that window open after the CLI exits so an error stays legible instead of flashing shut. `claude.ai` is opened in the browser again too, but before `auth login` now, not instead of it (v113.0): fixing the console alone was not enough — claude.ai's OAuth *authorize* endpoint has no account picker, so if the browser is already signed in as the old account, the CLI's login round-trip silently re-approves that same account through the existing session cookies, which is indistinguishable from "the switch did nothing". So the handler now opens plain `https://claude.ai` first and blocks on a message box asking the user to consciously sign out and into the desired account there — only after that confirmation does it run `claude auth login`, which then rides whatever account is now active in the browser. A second message box (reworded from the original "browser will open" text, since the browser step already happened) asks for confirmation once the CLI's own console-window flow (paste-a-code fallback included) is done, before `RelaunchNativeSessionAsync` fires
- Signed-in account label (v92.0, `claude auth status` in v112.0, WSL support in v113.0): `GetSignedInClaudeAccountLabel()` (NativeChat.cs) is the only synchronous, file-based source in the codebase for *which* Claude account is authenticated — the headless `system/init` event has no account/email field, so it reads `~/.claude.json`'s `oauthAccount.{displayName,emailAddress}` directly, the same state file the CLI itself owns. Best-effort (file is tens of KB, read is negligible next to the rest of a relaunch): any read/parse failure, including racing a CLI write, just returns null and callers show nothing. `BuildWelcomeFacts` still uses it for the passive "Signed in as ..." welcome-screen fact for the Windows provider, where a blocking CLI spawn on every session start would be a bad trade. `RelaunchNativeSessionAsync`'s `appendAccountLabel` path (only set by the Change Account handler) instead calls the async `GetClaudeAuthStatusEmailAsync(isWsl, ...)`, which shells `<resolved claude exe> auth status --json` (or `wsl.exe bash -lic "claude auth status --json"` for WSL) and falls back to the file-based label only if that subprocess call fails — a subprocess round-trip is negligible right after a full process relaunch, and it reads the same authoritative source the CLI itself just updated via `auth login`, rather than the undocumented json field. WSL path (v113.0): `GetSignedInClaudeAccountLabelAsync(isWsl)`/`InvalidateSignedInClaudeAccountLabelAsync(isWsl)` are the WSL-aware overloads — for `ClaudeCodeWSL` they resolve the distro's `$HOME/.claude.json` to its `\\wsl.localhost\` UNC form via `ResolveWslPathAsync` (a `wsl bash -lic "wslpath -w ..."` round-trip, the same approach `ResolveWslSessionDirectoryAsync` in `ClaudeCodeControl.SessionHistory.cs` uses for the transcripts directory) and then read/edit that file exactly like the Windows one. Because that round-trip can't run synchronously on the UI thread, `BuildWelcomeFacts` reads a `_wslAccountLabels` cache instead (keyed by provider, parallel to `_cliVersions`) and `BeginAccountLabelLookup` — mirroring `BeginCliVersionLookup` — fills it in the background and redraws the welcome card via `ShowChatWelcome` once the label is known, which is also what makes a brand-new WSL chat's welcome card show the signed-in account instead of staying silent forever (it previously read the Windows file for a WSL session, so unless the same account happened to be signed in on both sides, the label was always missing). Unlike `_cliVersions`, an empty result is never cached (fixed v113.0): every writer of `_wslAccountLabels` (`BeginAccountLabelLookup`, the resumed-transcript replay, and `RelaunchNativeSessionAsync`'s `appendAccountLabel` path) originally wrote `account ?? string.Empty` unconditionally, following the `_cliVersions` "ask once" convention — correct there because a CLI version genuinely cannot change mid-session, wrong here because "not signed in" routinely flips to "signed in" moments later (mid-login, or a slow write to the CLI's own state file after `auth login` returns). Caching a miss meant `BeginAccountLabelLookup`'s `_wslAccountLabels.ContainsKey(provider)` guard treated that miss as a permanent answer, so once any lookup raced a login that hadn't landed on disk yet, no later welcome card — including a brand-new chat — would ever probe again until the next explicit Change Account click. All three writers now skip the dictionary write entirely when the result is empty, leaving the key absent so the next render's `BeginAccountLabelLookup` retries
- `IsAgentAvailable` (NativeMode.cs, v89.0) is the "is there anything to send to" test — `IsNativeModeActive || (terminalHandle != IntPtr.Zero && IsWindow(terminalHandle))`. Three guards tested the window handle directly and so read as "no agent is running" for the whole of native mode: auto-send build errors and auto-send runtime errors both skipped silently, and the manual Send Build Errors button answered *"No agent terminal is running."* — even though all three deliver through `SendTextToAgentAsync`, which native mode supports. New unprompted-send paths must use this property, never the raw handle
- Call sites: end of `UpdateProviderSelection()`; `ToolsContextMenu_Opened` (`SyncShowUsageMenuCheckState()` + `UpdateSetWorkingDirectoryMenuHeader()` + refresh); `UpdateViewChangesButtonVisibilityAsync` (Diff.cs — now just re-runs the layout on workspace change); `RefreshSessionHistoryButton()` (delegates here). `UpdateDetachButtonIcon` keeps the menu item header, the `DetachToolbarButton` vector icon, and its tooltip in sync with the detached state
- `⚙` menu slimmed (v27.0): the seven configurable features moved out of the `⚙` menu into the Tools dropdown, so `⚙` now holds only the (flat) provider list, Configure Visible Agents, provider flags, Configure Custom Commands, Settings, About. (A provider submenu was tried and reverted — the flat list is preferred.)

## Custom CLI Paths (CliPaths.cs)

- Purpose: Per-provider override pointing each agent at a specific CLI executable instead of relying on PATH / the built-in native install location — for tools installed in non-standard locations
- Configuration: Stored as `Dictionary<AiProvider, string>` under `CustomExecutablePaths` in `claudecode-settings.json`; empty/whitespace entries are treated as unset
- Settings tab: Lives as the CLI Paths tab in the consolidated Settings dialog (`BuildCliPathsTabContent` builds the tab content; the host calls `ApplyCliPathChanges` on OK). Built programmatically in WPF (no XAML); a header note explains empty paths use default detection, then one aligned row per provider (from the static `CliPathProviders` table) with label + textbox; native (non-WSL) rows also get a "Browse..." `OpenFileDialog`. The Browse column width is reserved on every row so textboxes align even on WSL rows (no button). On OK, `ConfirmCliPathsBeforeClose` blocks the close (keeps the dialog open) with a Yes/No warning when any native path doesn't exist — Yes saves anyway, No returns to fix it. Only actually-changed entries are written; clearing a field removes it
- Resolution (`ResolveProviderExecutable`): returns the configured path (native → cmd.exe-safe double-quoted argument; WSL → Bash single-quoted word, with `'` escaped) or the default command when unset. Wired into `GetClaudeCommand`/`GetCodexCommand`/`GetDevinCommand`/`GetAntigravityCommand`/`GetCursorAgent*Command` and, since v111.0, `GetOpenCodeCommand`/`GetPiCommand` — those two branches of `StartEmbeddedTerminalAsync` (both CMD and WT paths) used to build their command inline and now call the helpers, so the model flag and the custom path stay in one place
- Detection (`CustomExecutableConfigured`): each `Is*AvailableAsync()` short-circuits to `true` when a custom path is configured (native validated with `File.Exists`, WSL trusted), so a tool off-PATH still reports available
- Apply: `ApplyCliPathChanges` returns the list of providers whose path changed. Any change runs `ClearProviderCache()` (detection results differ), but the terminal restart (folded into the Settings dialog's single `RestartTerminalWithSelectedProviderAsync()`) fires only when the active provider's path changed — editing an inactive provider's path doesn't disturb the running agent

## Model Catalog & Selection (Agents/ModelCatalog.cs, Controls/ClaudeCodeControl.ModelCatalog.cs, v111.0)

- Why it exists: before v111.0 only Claude and Devin had a model list in the extension; every other agent's model was whatever its CLI defaulted to, and native mode had no way to reach the CLI's own picker (it has no TUI). The catalog gives both surfaces — the terminal 🤖 menu and the chat composer — the same per-provider list
- Where each list comes from (measured against the installed CLIs, one command per agent): `codex debug models` (JSON), `cursor-agent --list-models` (`id - Display Name` lines), `opencode models` and `agy models` (one id per line), `pi --list-models` (a table whose provider+model columns are joined back into the `provider/id` pattern PI takes), and `reasonix doctor --json` (v123.0 — see the next bullet). Devin's ACP list is not reachable without a session, so it alone still falls back to a user-maintained list in the settings (`DevinModels`)
- Reasonix's list is per machine, and the values are provider names (v123.0): `reasonix --model` takes the `name` of a `[[providers]]` block in the user's `config.toml` — not a DeepSeek model id — so the valid set differs from machine to machine and anything else is rejected with `session/new: unknown model "…"`, which takes the whole native session down. Reasonix has no listing subcommand, but `reasonix doctor --json` reports `providers[]` with `name`, `models`, `is_default` and `key_present`, and `ParseReasonixProviders` reads exactly that (caption = `name — served models`, since the name alone says nothing about what answers). A provider with `key_present: false` is still listed: that is one environment variable away from working, and hiding it would leave no way to select it. This replaced a hard-coded list of model ids (`deepseek-v4-flash`, `deepseek-chat`, …) that was valid on no machine at all — see *Native Mode* for how it broke every launch — along with the "Configure Models…" dialog it fed and the `ReasonixModels` setting behind it. `DropRetiredReasonixModelSelection` (Settings.cs) clears a selection left from that list on first load, keyed off the absence of a `ModelCatalogs["Reasonix"]` entry so it runs once; without it the bad value would survive until the model menu was opened, which is *after* the launch it breaks
- Parsers are pure (`Agents/ModelCatalog.cs`, unit-tested in `Tests/ModelCatalogTests.cs`): the parse step strips ANSI escapes and `\r`, drops banner/prose lines, and dedupes case-insensitively (a WSL profile that echoes its command prints the list twice). `ParseCodexCatalog` keeps only `visibility == "list"` — the catalog also carries slugs Codex's own picker hides
- Fetching (`RunModelListingCommand`): Windows commands run through `cmd.exe /c` so an npm `.cmd`/`.ps1` shim resolves exactly as it does in the terminal, with PATH refreshed from the registry; WSL commands run through `wsl.exe bash -ic` (without `-i` an nvm-managed CLI is not on PATH). 30s timeout — Cursor authenticates and PI reads its provider registry, so this can reach the network — and the process tree is killed on timeout. stderr is drained and discarded (update notices and MCP banners would otherwise fill the pipe and block the exit)
- Caching: `_settings.ModelCatalogs[provider]` holds the list plus a UTC timestamp, 24h TTL. The menu always opens on the cached list; a stale or missing one is fetched in the background and dropped into the *already open* menu when it arrives (`RebuildProviderModelMenuItems` from the terminal menu, `FillChatModelMenu`'s continuation from the composer). `_modelCatalogFetches` collapses concurrent fetches for the same provider onto one process. A failed or empty fetch keeps the previous list — a CLI that is momentarily unreachable must not empty a menu that was working
- Stale selections: after a successful fetch, `DropSelectionMissingFromCatalog` clears a selection the CLI no longer offers, so a renamed/retired model falls back to the agent's default instead of being rejected at launch with no menu entry left to correct it
- How the selection is applied — three different mechanisms, by CLI:
  | Agent | Applied |
  |---|---|
  | Codex (both) | `-m <slug>` — launch flag (`GetCodexCommand`) and `CodexExecProtocol` |
  | Cursor Agent (both) | `--model <id>` — `GetCursorAgent*Command` and `CursorAgentProtocol`; with nothing selected native mode still asks for `auto` (a free plan refuses every named model) |
  | PI | `--model <provider/id>` — `GetPiCommand` and `PiSessionOptions.Model` |
  | Antigravity | `--model <id>` — `GetAntigravityCommand` and `PrintModeSessionOptions.Model` |
  | Open Code | `-m <provider/model>` — `GetOpenCodeCommand`; the TUI takes the same flag `opencode run` does (measured: a bogus id fails the turn, a valid one is echoed in the header), and it is the form `opencode models` prints. Native mode uses the ACP model picker instead |
  | Devin (both) | ACP `session/set_config_option` in native mode; `/model "<name>"` into the running TUI in the terminal (display names are not valid flags) |
  | Reasonix | `reasonix acp -model <provider-name>` at launch in native mode (`AcpSessionOptions.ModelLaunchArgument`, built by `AcpCommandBuilder.BuildReasonixModelArgument` — it publishes no `configOptions`); `/model <provider-name>` into the running TUI in the terminal |
- Settings shape: `SelectedProviderModels` is keyed by `AiProvider.ToString()`; Devin is the exception, read and written through the pre-existing `SelectedDevinModel` so its saved choice survives. An empty value means "the agent's default", which is a real menu entry in the composer ("Agent default") and cannot be requested over ACP — it always goes through a relaunch
- Long lists become submenus (`ModelCatalogGrouping`, pure/unit-tested): `cursor-agent` lists 193 models, which no flat menu can present. Over `FlatListLimit` (25) the list is grouped by family and each family becomes a submenu, in the order the CLI printed them; a family of one stays a plain entry (that is what keeps `auto` at the top). The key is the provider half of a `provider/model` id, otherwise the first two dash-separated segments — one segment lumps 88 of Cursor's models under `claude`, two split them into `claude-opus` (56), `claude-sonnet`, `claude-fable`. When grouping kicks in, the selected model is repeated as the first entry: inside a submenu the checkmark is invisible until the right family is opened
- Cursor's state marker is stripped (`StateMarker`): it prints `auto - Auto (current, default)` for whichever model is active. Only the words `current`/`default` are removed — the parentheses in the names themselves are meaningful (`Fable 5 1M (NO ZDR)`), and a marker cached in a caption goes stale the moment the model changes
- Composer submenus need their own style: `ComposerMenuItemStyle`'s template has no `Popup`, so a submenu built with it would open nothing — `ComposerSubmenuStyle` (ChatStyles.xaml) adds the arrow and the child popup, and both it and `ComposerMenuStyle` wrap the items host in a `ScrollViewer` (the stock templates this replaced scrolled; these did not, so a long list grew past the screen edge)
- Shared list editor: `ShowModelListDialog(agentName, models, description)` / `ShowModelNameDialog` (CustomCommands.cs) is the Devin list dialog, left parameterized after Reasonix stopped using it in v123.0

## Terminal I/O (TerminalIO.cs)

- Paste mechanism: Saves full clipboard state → sets text → pastes into the terminal → sends Enter → restores clipboard. For Command Prompt (conhost) the paste is handle-targeted (see below); for Windows Terminal it is Ctrl+Shift+V (`PasteViaCtrlShiftVAsync`)
- Handle-targeted conhost paste (issues #76, #82, #83, multi-instance): every Command Prompt (conhost) provider pastes via `PasteViaConhostPasteCommandAsync()` — `PostMessage(terminalHandle, WM_COMMAND, ID_CONSOLE_PASTE /*0xFFF1*/, 0)` posts conhost's own Edit→Paste command straight to the terminal window. This invokes conhost's clipboard paste regardless of QuickEdit/mouse-input mode, so it covers plain shells (Claude Code, Codex, Cursor) and TUIs that capture the mouse (Claude API-key sign-in, PI, Antigravity, Open Code) with no per-character keystroke flooding. Why handle-targeted: the earlier paths were all global input — plain `mouse_event` right-click, Shift+Right-click (Open Code), keyboard menu navigation (Antigravity/mouse-mode), Ctrl+Shift+V — which go to the foreground window / cursor position, so with two VS instances open (dev + F5 experimental, sharing one clipboard) the prompt leaked into the wrong instance's terminal. `WM_COMMAND` is addressed to a specific HWND, so the paste always lands in this instance's terminal. History: #76 first typed the prompt via per-character `WM_CHAR` for mouse-input mode, but TUIs answer each char with cursor-position queries → the duplicated `[Pasted text]` flood of #83 and PI's R-loop crash in #82
- Mouse-input-mode probe: `SendTextToTerminalAsync` still probes `IsTerminalInMouseInputMode()` once up-front (in AgentCompletion.cs — AttachConsole + `GetConsoleMode` on CONIN$, reusing the guarded console-attach machinery + `_consoleSnapshotLock` + std-handle hygiene; best-effort, false on failure) off the UI thread for conhost providers (`_wtTabBarHeight == 0`, excluding Open Code), but now only to skip the pre-deselect right-click (QuickEdit is off so there is no selection to clear and a right-click would just open the context menu). The paste mechanism itself is the same `WM_COMMAND` for all conhost regardless of the probe
- Keystroke path: the `WM_CHAR` keystroke send (`SendTextViaKeystrokesAsync`) is used only by the `DisableClipboardSend` send (non-PI conhost). PI never takes the keystroke path (UserInput.cs forces it onto the clipboard/`WM_COMMAND` paste, still writing large/disable-clipboard prompts to a temp file so the pasted reference stays short)
- Mouse-mode probe is tri-state (v72.0, #83): `IsTerminalInMouseInputMode()` returns `bool?` — `null` means the console attach / `GetConsoleMode` failed, which is not the same as "QuickEdit is on". `SendTextToTerminalAsync` treats `null` as "mouse captured" and skips the deselect right-click. Reporting unknown as `false` injected a real right-click into a TUI owning the mouse; each synthetic mouse event came back as a mouse-report escape sequence on the agent's stdin, which the CLI rendered as a runaway series of `[Pasted text #N]` blocks (only reproducible on Windows 10). Never widen `null` back to `false`
- Legacy Windows 10 console host (v72.0, #83): `IsLegacyWindows10Console()` (TerminalIO.cs) reads `CurrentBuildNumber` from the registry — not `Environment.OSVersion`, which the host manifest can shim — and caches it; `< 22000` = Windows 10. That host has no bracketed-paste support, so a paste reaches a TUI as ordinary keystrokes. Under it, UserInput.cs (a) forces prompts over the 1 KB threshold onto the temp-file reference regardless of `SendLargePromptsAsFile`, and (b) disables the `DisableClipboardSend` keystroke path so sends stay on the single handle-targeted `WM_COMMAND` paste
- Clipboard retry: Up to 10 retries with 100ms delay for `CLIPBRD_E_CANT_OPEN`
- Enter key varies by provider: `WM_CHAR` (Claude/OpenCode), `KEYDOWN/KEYUP` (WSL), double-Enter (Codex)
- Chunked paste: `SendTextToTerminalAsync()` splits text over `PasteChunkSize` (24 KB) into sequential pastes; each chunk waits a scaled post-paste budget (`500–800ms base + min(len/divisor, cap)`) so Enter (after the final chunk) never races a streaming paste. Provider paste + wait live in `TriggerPasteAndWaitAsync()`
- Large prompts as file (opt-in): when `SendLargePromptsAsFile` and the prompt exceeds ~1 KB, `SendButton_Click` writes it to `%TEMP%\ClaudeCodeVS_Session\<guid>\prompt-<ts>.md` and sends `Read and follow: <path>` — bypasses the conhost INPUT_RECORD buffer (truncates ~1 KB regardless of chunking), keeps `Files attached:` intact. WSL gets a converted path. Issue #48
- No trailing newline in payloads (issue #108, v71.0): both `SendTextToTerminalAsync` and `SendTextViaKeystrokesAsync` strip trailing `\r`/`\n` from the text before delivery (interior newlines preserved). Claude Code's TUI inserts a permanent blank line into its input box for every LF that reaches it outside a paste burst (a lone LF = Ctrl+J = insert-newline; a lone CR neither inserts nor clears — verified empirically against claude 2.1.215 under classic conhost by posting `WM_CHAR` 0x0A/0x0D). The prompt built by `SendButton_Click` ended in `\r\n` (`AppendLine`); on machines where conhost streams paste keystrokes slowly, the final LF landed outside the CLI's paste-burst window and left one blank line behind per send, accumulating over a session into a huge blank prefix carried by the next submitted message. Submission is always driven by `SendEnterKey`, so the trailing newline served no purpose. Do NOT try to "clean" residual blank lines by flooding Backspace before a paste — backspaces past an emptied input box showed nondeterministic side effects in testing
- Mouse pointer restore after send (v110.0, issue #122): Windows' "Hide pointer while typing" (`SPI_SETMOUSEVANISH`, on by default) hides the cursor with `SetCursor(NULL)` on each keystroke and normally restores it on the next mouse move, when the window under the pointer handles `WM_SETCURSOR`. That restore does not arrive here: `SetParent` permanently joins the embedded terminal thread's input queue with the VS UI thread (see issue #65), so both share one pointer-visibility state, and while an agent streams output the terminal thread can stop pumping long enough that the restoring `WM_SETCURSOR` is never processed — the pointer stays invisible until the user drifts over a VS window that is still pumping. Codex triggers it most because its TUI repaints continuously for the whole reply. Fix: `RestoreMousePointer()` (UserInput.cs, `#region Mouse Pointer Visibility`) calls `SetCursor` directly, bypassing `WM_SETCURSOR`, from `SendTextToTerminalAsync`'s `finally` (after every injected keystroke has been delivered) and at the end of `SendTextViaKeystrokesAsync`; `PromptTextBox_PreviewKeyDown` uses it too instead of its old inline `SetCursor`. The shape comes from `IsPointerOverTerminal()` — Win32-only (`GetCursorPos` + `GetWindowRect`, no WPF hit test, safe from any thread) — arrow over the terminal, I-beam elsewhere, so the correction is invisible; a real mouse move re-asserts the proper cursor through the normal path anyway. Do not try to re-assert the cursor from the low-level mouse hook on every `WM_MOUSEMOVE`: `ShouldDispatchMouseHookMessage` exists precisely to keep those high-frequency events off the dispatcher, and the hook thread is outside the relevant input queue
- Synthetic right-click restores pointer position (v110.0, issue #122): `SendRightClickAsync`/`SendRightClick` (the pre-deselect click for conhost) `GetCursorPos` before `SetCursorPos` and put the pointer back afterwards. Parking it at the terminal centre is what made "my mouse disappeared" so hard to recover from — the pointer was both hidden by hide-while-typing and no longer where the user had left it
- Clipboard verification: `SetClipboardAndVerifyAsync()` sets then reads back the clipboard before each paste — guards against a clipboard manager (Win+V, Ditto, RDP) overwriting it mid-send. Tolerant compare (`ClipboardTextMatches`) normalizes line endings/trailing `\0\n`. Retries 3× with 150ms backoff; on persistent failure logs and pastes anyway (issue #59). Contention → enable `DisableClipboardSend` (issue #61)

## Claude Usage (Usage.cs / ClaudeUsageControl / ClaudeUsageToolWindow)

- Tool window: Embeds `claude.ai/settings/usage` in a WebView2 control (`ClaudeUsageToolWindow`, GUID `C3D4E5F6-...`); opened via toolbar or menu
- X-button behavior: Intercepted via `IVsWindowFrameNotify2.OnClose` — calls `frame.Hide()` and returns `E_ABORT` so the WebView2 scraper keeps running in the background
- `ForceClose()`: Toolbar toggle calls this to fully destroy the window (WebView2 disposed); distinct from X-button hide
- Inline usage bars: Mini progress bars in the prompt panel showing session/weekly usage; populated from `UsageSnapshot`; hidden when scraping fails or user not signed in
- Snapshot caching: Last successful scrape serialized as JSON to `LastUsageJson` + `LastUsageTimestamp`; restored on startup so bars render immediately with stale data while fresh fetch runs
- Auto-refresh: `UsageAutoRefreshSeconds` setting (0 = manual); page reload triggered by visible tool window's scraper — no background WebView2 to avoid focus contention. Off/2m only (v67.0): the 30s/1m/2m/Off combo (both in the tool window toolbar and the Settings *Usage* tab) collapsed to a single Auto-refresh checkbox meaning 0 (off) or 120 s — the sub-2-minute intervals reloaded the page faster than claude.ai's usage data actually changes. Because older releases persisted 30/60 into JSON, every read path floors a positive value to 120 (`ApplyAutoRefreshSeconds`, `StartUsageBackgroundRefreshTimer`, and the Settings dialog's `origAutoRefresh`) rather than migrating the field, so a legacy value is normalized wherever it enters. The background floor for the "Off" case stays 60 s (inline bars still need a slow refresh when the tab is closed)
- Session restore: `UsageWindowOpened` persisted; `InitializeUsageMonitoring()` auto-reopens the window and reloads data 2s after solution load
- User-data folder (persistence): A single fixed `%LocalAppData%\ClaudeCodeExtension\WebView2` folder holds the WebView2 profile so cookies/localStorage/IndexedDB survive a VS restart (devenv gets a new PID each launch — the old per-PID folder started every session logged-out, issue #62). `ClaudeUsageWebViewEnvironment.GetOrCreateAsync(primary, fallback)` falls back to a per-PID `WebView2_<pid>` folder only if `CreateAsync` throws because another VS process holds the lock. `CleanupStaleWebView2Folders()` reclaims dead `WebView2_*` folders (glob excludes the fixed `WebView2`). `shared_cookies.json` (`Load/SaveSharedCookiesAsync`) is a DPAPI-protected secondary fallback restore path; legacy plaintext payloads are read once and rewritten protected on the next save
- Bar role: `meter` (was `progressbar`) + language-independent parsing (v54.0): Claude.ai's usage page switched the bars from `[role=progressbar]` to `[role=meter]` (inside `data-cds=Meter`) and localizes all labels ("Sessão atual"/"Todos os modelos"/"Fable"). The scraper had queried `[role=progressbar][aria-valuenow]` everywhere, so it found zero bars → `extract()` returned null (inline bars kept showing the stale cached snapshot) and page isolation found no target (full settings page with sidebar rendered instead of the trimmed block). Fixed by matching both roles via the `BAR_SEL`/`BAR_ROLE_SEL`/`isBarRole()` helpers (kept dual so a revert or cached page still parses) across `findSection`, `findIsolationTarget`, `clearStaleInlineWidths` (must skip meter descendants too, or it wipes the inline fill `width:63%`), the trim CSS, and `extract`. Row identification is now language-independent: labels read via `aria-labelledby`→`getElementById` (`readBarLabelAndReset`) with the `.text-primary` column as fallback, session/weekly matched by multi-language keyword regex but ultimately by document order (session = first bar; weekly = the aggregate "all models" bar, which always precedes per-model bars like Fable — so weekly falls back to "first row after session", never a per-model bar). `readUsedPercent` prefers `aria-valuetext` ("63% usado"/"63% used") so extra-usage percent survives localization and the >100% case. The old `div[tabindex=-1].outline-none` isolation target is gone from the page; the bar→`closest('section')`→`parentElement` (`div.pb-8`) fallback now supplies it. Pure JS fix — `UsageSnapshot` field names and the C# side are unchanged
- Corporate proxy interstitial handling (`TryHandleUrlBlock`): Detects when `core.Source` ends with `/urlblock.php` (iboss/Forcepoint/Zscaler style block pages) and injects a JS poller that retries up to 25× at 200ms looking for the Continue submit button — multiple selector fallbacks (`input[type=submit][name=ok]` → generic `input[type=submit]` → `button[type=submit]` → `button[name=ok]` → `form.submit()`). Works while the tool window is hidden because CoreWebView2 processes navigation and JS without a visible rendering surface. Throttled to one click per 3 s. Triggered from both `OnNavigationCompleted` and `OnSourceChanged`
- Scrollbox preservation (v73.0): `isolatePath()` used to mark *every* ancestor between the isolation target and `<body>` as `data-claude-usage-path`, whose CSS forces `display:block; height:auto; overflow:visible` — this silently deleted claude.ai's own internal scroll pane (a `flex-1 min-h-0 overflow-y-auto` wrapper around the settings content), so anything below the initial fold (e.g. the Usage Credits spend/balance/buy-credits rows) was unreachable with no scrollbar at all. Fix: while walking up, the first ancestor whose *native* computed `overflow-y` is `auto`/`scroll` (checked before any of our own attributes could affect it) is tagged `data-claude-usage-scrollbox` instead of `-path`; every further ancestor above it is tagged the same way (`pastScrollbox` flag) since they're all part of its flex height-bounding chain. The `scrollbox` CSS rule only strips width caps/grid columns — it never touches `display`/`height`/`overflow`, so the pane's native scrollbar keeps working exactly as it does in a real browser tab.
  - Follow-up — the `keep` rule was the same bug (v73.0): the ancestor-side fix alone didn't restore scrolling, because `findIsolationTarget()` can resolve to a `tabindex=-1` dialog shell (not just the small `div.pb-8` block) when the page has one — that shell itself commonly uses `display:flex; flex-direction:column` to stack a header above the internally-scrolling body. The `[data-claude-usage-keep="1"]` rule was still forcing `display:block !important` on the target, which collapses that flex-column and strips the scrollable child's bounded height (its `flex-1`/`min-h-0` become no-ops once the parent isn't a flex container) — the shell's own untouched `overflow:hidden` then just clips the excess with no scrollbar, no matter what the ancestor-side fix does. `keep` now only widens the target (`width`/`max-width`/`margin`/`box-sizing`) and leaves `display`/`height`/`overflow`/`padding` completely alone, same principle as the `scrollbox` rule.

- `_isInitializing` guard: Prevents `SaveSettings()` during `LoadSettings()`
- `[JsonExtensionData]`: Preserves unknown JSON properties across DLL versions

## Workspace (Workspace.cs)

Priority: DTE solution dir → active project dir → IVsSolution dir → current dir with `.sln`/`.csproj` → My Documents

Workspace-change coalescing (issue #73, 10.98): solution load fires `OnWorkspaceDirectoryChangedAsync` in a burst — `OnAfterOpenSolution` (500ms delay), `OnAfterOpenProject` once per project (300ms delay), plus the control's startup init. Each overlapping call used to pass the racy `cmdProcess == null` / stale `_lastWorkspaceDirectory` checks and queue its own terminal launch, producing launch→stop→relaunch×3 churn of fresh WSL sessions (visible in terminal-launch.log) — the direct trigger for the WSL-teardown-contention blank-panel failures. The public method is now a coalescing wrapper (UI-thread flags `_workspaceChangeInProgress` / `_workspaceChangeRerunRequested` / accumulated forceDiffReset): one evaluation (`HandleWorkspaceDirectoryChangedAsync`) runs at a time, a burst collapses into a single trailing re-run that sees the terminal already in the right directory and does not restart it.

Per-solution custom working directory (issue #100, v53.0): `_settings.CustomWorkingDirectory` used to be a single extension-wide value, so opening a different solution kept whatever directory the last one had set. `ProjectWorkingDirectories` (`Dictionary<string,string>` keyed by `GetCurrentSolutionName()`, the precedent from `ProjectAgentFinish`) now holds a per-solution override; `GetEffectiveCustomWorkingDirectory()` returns the entry for the current solution when one exists, else falls back to the global `CustomWorkingDirectory` (also the only path used for "Open Folder" workspaces, which have no solution name to key by). `GetWorkspaceDirectoryAsync()` and the *Set Working Directory* menu header (`ProviderManagement.cs`) both read through this helper; the menu's click handler writes into `ProjectWorkingDirectories` when a solution is open (removing the entry when the field is cleared) and only falls back to writing the global field when there is none.

Native mode survives a same-directory reload (v112.0): `HandleWorkspaceDirectoryChangedAsync`'s "terminal not initialized yet" branch used to gate entirely on `HasTerminalLaunchState()`, which only checks the classic terminal's handle/`cmdProcess` — always false while native mode is active, since it never sets those. A VS project reload (`OnAfterOpenProject` fires even when reopening the same project) therefore always fell through to `InitializeTerminalAsync()` → `TryStartNativeModeAsync()`, which unconditionally tears down and recreates the agent session, silently dropping the conversation. Fixed with a guard ahead of the existing check: when `IsNativeModeActive && WorkspaceDirectoriesEqual(_lastWorkspaceDirectory, newWorkspaceDir)`, the handler only re-runs diff tracking/baseline reset and returns, leaving the live session alone. A genuine workspace/solution change still falls through and restarts it, same as before. Terminal mode was never affected — `HasTerminalLaunchState()` already stays true for it across a reload.

## Theme (Theme.cs)

- Two distinct colors: `terminalPanel.BackColor` is the live WPF panel color; `_terminalAgentColor` is the color the embedded terminal/agent was launched with. Theme-change prompts compare these two — the panel can drift away from the agent color across multiple theme switches without restarting the agent
- Agent color set only on launch: `RecordTerminalAgentColor()` is called at the end of both successful embed paths in `StartEmbeddedTerminalAsync` (WT and CMD). It snapshots `terminalPanel.BackColor` and persists it as `LastAgentTerminalColorArgb`. Never updated by `UpdateTerminalTheme` (which only re-tints the panel)
- Restart prompt skip conditions: No prompt when (a) a forced theme is active (`SelectedThemePreference != Automatic`), (b) terminal isn't running, or (c) `terminalPanel.BackColor == _terminalAgentColor` — covers two-dark-themes-same-RGB and reverting to a previously-declined color
- Re-entrancy guard: `_isShowingThemeRestartPrompt` prevents a second "Theme Changed" `MessageBox` stacking on the first. WPF dispatcher keeps pumping during the modal, so a later debounce tick from another `VSColorTheme.ThemeChanged` event would otherwise open a second dialog
- Debounce: 500ms `DispatcherTimer` collapses rapid consecutive theme events into one prompt
- Forced theme overrides: `ApplyForcedThemeResources()` injects 9 VS brush keys into the control's `Resources` dictionary so child WPF elements pick up the forced palette via `DynamicResource`. Removed when reverting to Automatic
- Custom background color (`ThemePreference.Custom` + `CustomThemeColorArgb`, default #F4ECFF): `GetCustomThemeColor()` returns the color; `ApplyForcedThemeResources()` derives fg (black/white) + hover/border shades from its brightness. Set in Settings → Theme via hex box + `ColorDialog`
- Console colors written for every theme (`SaveAndSetConsoleColorsRegistry`): the conhost background is set from `GetTerminalBackgroundColor()` (the current theme's bg — custom/dark/light/automatic alike) by writing `ColorTable00` (BGR) explicitly on every launch, `ColorTable07`=black/white by brightness, `ScreenColors`/`PopupColors`=`0x07` (bg index 0, fg index 7). Earlier code left `ColorTable00` untouched for non-custom themes and relied on the registry's existing value, so a leftover custom color stuck after switching back to Automatic/Dark/Light. Two guards prevent the custom color from being baked in permanently: (a) the explicit `ColorTable00` write overrides any stale value at launch, and (b) if `_consoleColorsSaved` is still true on entry (a prior launch saved originals but a superseded/aborted relaunch — issue #73 churn — skipped the restore), `RestoreConsoleColorsRegistry()` runs first so the *true* user originals are recovered before re-saving, instead of capturing the temporary themed color as the "original" that every later restore would write back. Light-theme accent palette (issue #80): writing only `ColorTable00`/`07` left the 14 accent slots (`ColorTable01-06`, `08-15`) at their dark-tuned defaults, so on a light background the agent's cyan/blue tokens washed out. `WriteThemedConsolePalette()` now, when `Brightness(bg) > 150`, also paints a darker/saturated full palette from `GetLightConsolePalette()` (bright slots 09-14 mirror their normal counterparts so bright accents stay legible). All 16 slots are saved into `_savedConsoleColorTable[]` and restored (dark themes still leave the accent slots untouched)
- Opt-out: `SkipThemeRestartPrompt` setting (exposed in the consolidated Settings dialog) short-circuits `OnThemeChangeDebounceTimerTick` entirely — for users who auto-swap themes mid-session (e.g. VS debugging theme on F5) and don't want to be asked

- Single entry point: `Settings...` menu item in the ⚙ context menu, consolidating all previously-scattered toggles
- Tabbed layout: `ShowConsolidatedSettingsDialogAsync()` builds a themed `TabControl` with six tabs via the local `AddTab(header)` helper: Behavior (send-key mode, large-prompt/clipboard sending, auto-open changes, don't-bring-to-front, prompt font size, On Agent Finish button), Layout (prompt-panel position, hide prompt input box), Terminal (terminal type, console font), Theme (theme preference incl. custom-color hex box + `ColorDialog` picker, skip-restart-prompt), Usage (show inline bars, auto-refresh), CLI Paths (per-provider custom CLI executable paths — content built by `BuildCliPathsTabContent`, applied via `ApplyCliPathChanges`). - Toolbar tab: `BuildToolbarButtonsTabContent()` builds a drag-and-drop reorderable list (one `Border` row per `ToolbarButton`, Tag = the feature, ⠿ grip handle) with a promote-to-button checkbox each. WPF `DragDrop`: a drag starts only from the ⠿ grip (its `PreviewMouseLeftButtonDown` captures the mouse; `PreviewMouseMove` releases capture and calls `DoDragDrop` past the system drag threshold). Only the grip carries the `SizeAll` cursor — the checkbox/label keep the regular pointer and the checkbox toggles normally. - Console font size (Terminal tab): a point-size combo (`Default` + 6–36 pt) feeding `ConsoleFontSizePt` (`0` = terminal default), applied by `Terminal.cs` as a conhost `FontSize` registry DWORD (`pt→px`, `(px<<16)`) and a Windows Terminal profile `font.size` (points). A size change (like a face change) relaunches the terminal. The terminal always starts at exactly this size; under Command Prompt a Ctrl+Scroll zoom updates it automatically (v78.0), so the combo also reflects whatever the user last zoomed to, while under Windows Terminal the zoom stays live-only and this combo is the only persistent control. See "Console font / codepage registry" and "Console font under Windows Terminal"
- Console font picker (Terminal tab): searchable list of installed families feeding `ConsoleFontFaceName` (default `Cascadia Mono`), which `Terminal.cs` pushes into the conhost registry (`FaceName` + `FontFamily=54`) and into a dedicated Windows Terminal profile (`font.face`, launched with `-p`). - Terminal tab landing mid-scroll instead of at the top (v117.0): the console/chat font pickers (`fontList`/`chatFontList`) call `ScrollIntoView()` on their selected item once loaded, so a saved font that's mid-list starts visible. `RequestBringIntoView` bubbles past the list's own internal `ScrollViewer` into the Terminal tab's outer page `ScrollViewer` (every `AddTab` tab is wrapped in one), which then also scrolls the whole page to keep that mid-page list in view — so the dialog opened with the Terminal tab scrolled to the middle instead of the top. ## Session History (SessionHistory.cs)

- Scope (v132.0): Claude Code and Codex, each in native Windows and WSL. Claude keeps the original direct-JSONL path; Codex uses its App Server thread API because rollout file layout and state metadata are provider-owned details
- Surfacing: `SessionHistoryViewMenuItem` (in the `☰` Tools dropdown) or, if promoted, `SessionHistoryToolbarButton` — always shown now (issue #97); `ShowSessionHistoryDialogAsync` explains that Claude Code or Codex is required for other providers. Placement is handled by `RefreshToolbarLayout()` (`RefreshSessionHistoryButton()` delegates there)
- Path encoding: `EncodeClaudeProjectPath()` replicates Claude Code's filesystem encoding: every non-alphanumeric char → `-`. Example: `C:\Users\Daniel` → `C--Users-Daniel`
- Directory resolution: Native → `<config>\projects\<encoded-cwd>`, where `<config>` comes from `GetClaudeConfigDir()` — it honors the `CLAUDE_CONFIG_DIR` env var (the same one the CLI reads, supports `%VAR%` expansion) and falls back to `%USERPROFILE%\.claude` when unset/blank, so a relocated data store (e.g. on another drive) is found. WSL → shells out `wslpath -w "${CLAUDE_CONFIG_DIR:-$HOME/.claude}/projects/<encoded>"` (so a relocated config dir *inside* WSL is honored via the login shell's env) to get a `\\wsl.localhost\` UNC path readable by .NET. The WSL lookup drains stdout/stderr asynchronously and is bounded by a 5s timeout so a cold or hung WSL instance cannot leave the dialog loading forever
- `GetClaudeConfigDir()` is the shared `.claude`-root resolver
- JSONL parsing: `ParseSessionFile()` reads with `FileShare.ReadWrite` (so the active session file isn't locked); extracts first user-typed message as preview, skips `tool_result`/`image` parts, sums `input_tokens + output_tokens` from assistant lines
- Codex discovery (v132.0): `Agents/CodexAppServerClient.cs` launches the selected environment's `codex app-server --stdio`, performs the mandatory `initialize` → `initialized` handshake, pages `thread/list` with the exact workspace `cwd`, and uses `thread/read {includeTurns:true}` / `thread/delete`. Native uses the configured/resolved Windows executable; WSL runs the configured Linux command under `wsl.exe bash -ic`, changes to the `/mnt/<drive>/...` workspace, and therefore reads the distro's own `CODEX_HOME` rather than the Windows store. Each operation owns a short-lived process and disposes it when complete. The JSONL response line can contain an entire transcript, so it reuses `JsonLineProcessHost`'s unbounded UTF-8 line pump. Request ids are matched while unsolicited notifications are ignored; requests time out after 20 seconds and keep a bounded stderr tail for useful errors
- CLI-injected lines are skipped (#121): `IsMetaTranscriptLine(obj)` drops any record carrying a top-level `isMeta: true` — local-command caveats and skill expansions the CLI writes on the user's behalf, which Claude Code's own UI hides. They arrive as ordinary `user`/`assistant` lines with real text, so neither the type filter nor the `tool_result` check catches them, and they were being counted as messages and picked up as the preview. Only the JSON boolean `true` counts: a plain `(bool?)token == true` would coerce the *string* `"true"` and throw `FormatException` on anything it can't parse, so a future CLI writing a non-boolean there would change what the list shows or break the read outright. The check sits before the type dispatch (skill expansions land as `assistant` lines too) but after the `cwd` read, so a session whose first record is a meta line keeps its originating directory. `BuildReadableTranscript()` applies it as well — the largest meta line seen in the wild is 863 KB of skill prompt, which would drown the exported text
- Command-only sessions are hidden (v106.0): typing a slash command (`/effort medium`) makes the CLI expand it into a literal `<command-name>…</command-name>` block stored as a *user* message — no `isMeta` flag, so the filter above doesn't reach it. `IsCommandInvocationText(text)` matches those on the trimmed start; they never count toward `MessageCount` or the preview, and `ParseSessionFile` returns null when a transcript consists of nothing else (`messageCount == 0 && sawCommandInvocation`), so single-command sessions stop cluttering the list. A session with both real turns and commands is kept — only the command rows are ignored. Both helpers are `internal static` for `Tests/SessionTranscriptFilterTests.cs`
- Dialog: WPF modal built programmatically; loads sessions async after open (shows "Loading…" placeholder); supports Resume, Resume Last Session, View, Rename, Delete and Refresh for both providers. Claude list summaries include messages/tokens parsed from disk; Codex `thread/list` deliberately does not load every full transcript just to compute counts, so unavailable counts are omitted instead of shown as zero. Layout (v35.0): a top filter bar (search box + "Renamed only" checkbox), the list, then a `DockPanel` button row with Refresh docked left and the launch/destructive actions grouped right. `CreateSessionItemContent()` builds each row as a `Grid` (left accent bar + stacked dim-meta line and title/preview line) and `BuildSessionTooltip()` the tooltip
- Filtering (v35.0): the full set is held in `loadedSessions`; `applyFilter()` is the single render path — it rebuilds the `ListBox` from `loadedSessions` applying the search text (matches custom title / preview / date, case-insensitive) and the "Renamed only" toggle, preserves selection by `SessionId`, and shows a "No sessions match" placeholder when the filter empties a non-empty list. `loadAsync()` fills `loadedSessions` then calls `applyFilter()`; search `TextChanged` and the checkbox events also call it. Rename/Delete mutate state then call `applyFilter()` to re-render (so the renamed-row layout and any active filter both update)
- Rename / custom titles (v35.0, issue #95): a custom title can be set via the Rename button, the list's right-click context menu, or F2. `ShowRenameSessionDialog()` is a small themed input box prefilled with the current title; an empty result clears the override. Titles persist in `_settings.SessionCustomTitles` (`Dictionary<string,string>` keyed by session UUID, case-insensitive), saved via `SaveSettings()`. `LoadSessionsAsync()` populates `SessionInfo.CustomTitle` from that dict after parsing. A renamed row is rendered distinctly (lavender accent bar + bold accented title with a `✎` marker); the original auto-preview moves to the tooltip. Deleting a session also removes its title entry
- Resume flow (v132.0): `ResumeSessionAsync()` sets `_pendingResumeSessionId` and forces the provider to the session's owning environment before restart. Claude consumes it as `--resume <id>`; Codex terminal mode consumes it as `codex ... resume <id>`, while native mode seeds `OneShotSessionOptions.ResumeSessionId` so its first prompt is `codex exec resume <id> -`. "Resume Last" keeps Claude's `--continue`; for Codex it resolves the newest `thread/list` row to an explicit id first, which makes terminal and native mode identical. Codex View/replay uses `thread/read`, and Delete uses `thread/delete` rather than removing only the rollout file; because Codex can delete spawned descendants with their parent, the confirmation says so explicitly
- View (v48.0; Codex added v132.0): a View button + right-click View… item render the selected transcript as readable plain text written to `%TEMP%\ClaudeCodeExtension\SessionView\session-<uuid>.txt` and opened with the shell default (`Process.Start(UseShellExecute)`, i.e. Notepad). Claude reads its JSONL through `BuildReadableTranscript`; Codex reads provider-neutral `userMessage` / `agentMessage` / tool markers from `thread/read` through `BuildReadableCodexTranscript`. Read-only — never modifies the original transcript. Header (title/id/cwd/modified/counts/path) then each turn in order: `USER [ts]:` / `ASSISTANT [ts]:`, timestamps converted to local time. Title always leads the header (v128.0, issue #126): it used to be emitted only for a renamed session, so an untitled export carried no name and nothing could lift an issue title out of the file. It is now the first line and always populated, resolved by `SessionInfo.DisplayTitle` (custom title, else preview) and passed through `NormalizeTranscriptTitle()` — whitespace runs (including embedded newlines/tabs a pasted rename can carry) collapse to single spaces, capped at 120 chars + `…` to match the preview cap, `(untitled session)` for blank. `internal static` for `Tests/SessionTranscriptFilterTests.cs`

## On Agent Finish (AgentCompletion.cs)

- Scope: any agent running in the Command Prompt (conhost) terminal — detection reads the console screen buffer, so it is provider-agnostic. Windows Terminal supported (v41.0): the embedded WT window belongs to `WindowsTerminal.exe`, not the cmd.exe inside its ConPTY, so the watcher attaches to the ConPTY console client resolved at launch (`_wtConsoleClientPid`) and reads the same real screen buffer — alternate-screen TUIs (e.g. Devin) are detected and the read is cursor-blink independent. If that client can't be resolved/read, the watcher falls back to the UI Automation path (`_watchViaUia` / `TryCaptureWindowsTerminalText`, WT's UIA Text pattern). Default disabled. Configured in its own window (`ShowAgentFinishSettingsDialogAsync`, AgentFinishDialog.cs) opened from a button in the consolidated Settings dialog. UI: the "On Agent Finish…" button stays enabled for both terminal types; under WT an informational hint is shown (`SyncAgentFinishAvailability()`, wired to the terminal-type radios like `SyncDisableClipboardAvailability()`)
- WT ConPTY client resolution: just before launching WT, `StartEmbeddedTerminalAsync` snapshots existing cmd.exe PIDs (`SnapshotCmdProcessIds()`) and resets `_wtConsoleClientPid = 0`; after the WT window is embedded it calls `ResolveWtConsoleClientPid(preExistingCmdPids, terminalHandle)` (short retry loop). Window-scoped match (fix, v50.0): it first resolves the new WT window's owning process via `GetWindowThreadProcessId(terminalHandle)` and looks for the new cmd.exe among *that process's* descendants only — this is what ties the result to the exact terminal just embedded. Only when that HWND isn't available/alive does it fall back to the old unscoped scan (new cmd.exe that is a descendant of *any* `WindowsTerminal.exe`), or the sole new cmd.exe if the tree walk lags. The unscoped scan alone was the bug: with two VS instances (or a fast restart before the old shell exits) launching WT around the same time, `newCmd` can hold more than one candidate and the old code returned the first `HashSet` match regardless of which window it belonged to — silently attaching the watcher to a different session's console, so detection read the wrong buffer and never lined up ("Windows Terminal detection not working properly"). Reset to 0 in `StopExistingTerminalAsync`. `TryCaptureConsoleText`/`TryCaptureConsoleHash` take an optional `directClientPid` that bypasses `ResolveConsoleClientPid` (window-based) and attaches straight to this PID; the tick passes `_watchedClientPidDirect`
- Global default + per-solution override: the effective config is resolved by `GetEffectiveAgentFinish()` — returns `_settings.ProjectAgentFinish[<solution name>]` when the open solution (keyed by `.sln` name via `GetCurrentSolutionName()`) has an entry, else the global `_settings.AgentFinish`. The watcher captures the effective config into `_watchedAgentFinish` at arm time so a mid-turn solution switch can't swap it. The dialog edits in-memory working copies (`CloneAgentFinish`) and on OK writes the global back and upserts/removes the per-solution entry. Mid-turn settings edit: after the dialog saves, it calls `RefreshWatchedAgentFinishConfig()`, which — only when a watch is currently active — re-resolves `GetEffectiveAgentFinish()` into `_watchedAgentFinish` so the just-saved settings apply to the in-flight turn when it finishes (and stops the watcher if the feature was turned off). The fire path already reads `IdleSeconds`/the action from `_watchedAgentFinish` live, so the swap takes effect for the current turn. (Enabling the feature mid-turn when it was off at arm time stays a no-op — no baseline/prompt-time was captured — so it applies from the next prompt)
- Console-attach leak guard (critical): the watcher `AttachConsole`s VS itself each tick. If VS is left attached, the next `conhost.exe` spawn inherits VS's console instead of creating its own window and the terminal renders blank (issue #73: "Restart code agent" stayed blank until VS was reopened; also visible after switching solutions). Three guards: `ResetAgentCompletionWatcher()` stops the watcher + dismisses the info bar on `OnBeforeCloseSolution`, the workspace-changed branch of `OnWorkspaceDirectoryChangedAsync`, and at the top of every `StartEmbeddedTerminalAsync()` (covers the restart button, provider/model switches, theme restarts, session resume); `EnsureNoConsoleAttached()` calls `FreeConsole` under a bounded `_consoleSnapshotLock` (`Monitor.TryEnter` w/ timeout), run after `StopExistingTerminalAsync()` and at the start of `ExecuteAgentFinishActionAsync` (no-op when VS has no console); and the conhost `Process.Start` itself runs inside a bounded `_consoleSnapshotLock` acquire + `FreeConsole` (background thread, 5 s timeout), so an in-flight capture can never overlap CreateProcess and a stuck attachment is cleared immediately before the spawn
- Std-handle restore (critical, the v14.0 fix for the OAF restart repro): `FreeConsole` alone is NOT enough — `AttachConsole` replaces devenv's standard handles with handles into the agent's console and `FreeConsole` leaves them dangling. Once the agent's console dies (restart kill), every later `conhost.exe -- cmd.exe` spawn inherits the dead std-handle values and exits within ~100 ms with code 0, so the panel stayed blank until VS was reopened no matter what the guards freed (reporter's repro: only after an OAF notification had fired — i.e. only after at least one capture had run). Fix: `CaptureOriginalStdHandlesOnce()` snapshots devenv's true originals before the first attach ever (static, process-wide); `RestoreOriginalStdHandles()` (`SetStdHandle` ×3) runs after every capture's `FreeConsole`, inside `EnsureNoConsoleAttached()`, and right before the conhost `Process.Start` (which logs `stdHandlesWereDirty=` so a user's terminal-launch.log can confirm/rule out this cause)
- Arming: `ArmAgentCompletionWatcherAsync()` is fired (fire-and-forget) at the end of `SendButton_Click`. Terminal-typed prompts (v80.0): it is also armed from `LowLevelKeyboardHookCallback` when Enter is pressed with the embedded terminal focused and no watch is active — prompts typed directly into the terminal bypassed `SendButton_Click` entirely, so the feature never fired for those turns (the main "flaky" report). The `!_completionWatchActive` guard keeps a mid-turn Enter (menu choice, y/n answer) from re-arming and resetting the turn's baselines; an Enter that produces no screen change (empty input) never fires because `_consoleSawActivity` stays false. Stores the conhost PID (`cmdProcess.Id`), takes an initial screen snapshot and send time, then starts `_agentCompletionTimer` (1 s `DispatcherTimer`). For Claude Code it also records a token baseline (newest `*.jsonl` via `CountTranscriptTokens`) to enrich the notification — not used for detection. Re-arming resets state; `StopAgentCompletionTimer()` also runs from `CleanupResources()`
- Console-client PID: the terminal launches as `conhost.exe`, but `AttachConsole` needs a console *client*, so `ResolveConsoleClientPid()` derives the cmd.exe PID from `GetWindowThreadProcessId(terminalHandle)` (returns the client by Windows back-compat) and falls back to the conhost's first ToolHelp32 child. Resolved fresh each sample so a restart can't pin a dead PID
- Completion detection (`OnAgentCompletionTimerTick` → `TryCaptureConsoleText`): each tick resolves the client PID, then `SetConsoleCtrlHandler(NULL,TRUE)` (shield VS from a shared-console Ctrl+C) → `AttachConsole` → `CreateFile("CONOUT$")` → `ReadConsoleOutputCharacter` → `FreeConsole` → restore Ctrl+C (all under `_consoleSnapshotLock`). Visible text plus cursor pos is FNV-1a hashed (`ComputeStableHash`); a changed hash ⇒ agent working. Fires only when activity was seen this turn and the hash held unchanged ≥ `IdleSeconds` (default 5, clamped 2–120). Dead PID disarms; the watch also gives up after 30 min without a single screen change (`AgentCompletionMaxIdleMinutes`, v80.0 — was a fixed 30-min *total-watch* cap, which silently disarmed long turns where the agent was still actively producing output, so their finish notification never fired). Waiting-for-input suppression: a static y/n or selection prompt reads as idle, so the settled screen is classified by `LooksLikeAgentInputPrompt()` (`AgentPromptKeywords` + `❯`/numbered-menu over bottom ~18 lines); on a match the tick returns without firing/disarming (and sets `_awaitingAgentInputReply`), so it fires once the user answers. Conservative by design. Numbered-list false-positive fix (v27.0): a numbered *menu* is recognized only together with the `❯`/`›`/`▶` selection cursor (`sawArrow && menuItems >= 1`); the earlier "two-plus numbered options ⇒ prompt" rule made a finished turn whose final answer ended in a numbered list read as a waiting prompt, so the watcher backed off and the notification never fired. Real Claude Code selection/permission boxes always render the cursor, so genuine prompts stay suppressed while list-ending answers complete. Prose-keyword false-positive fix (v46.0): the broad phrases `do you want to` / `do you trust` / `allow this` / `allow command` were removed from `AgentPromptKeywords` for the same reason — real permission/trust/choice boxes that use them also draw the `❯` cursor + numbered options (already caught structurally), but a *finished* turn whose prose answer merely ended with "Do you want me to …?" matched the keyword and was mis-suppressed, so the notification "sometimes never fired." The keyword list now keeps only waiting-state markers that render without a selection cursor (`(y/n)`/`[y/n]`/`(yes/no)`/`press enter to continue`/`press any key`). Classic-renderer cursor + footer fix (v52.0): Claude Code's non-alternate-screen renderer draws the selection cursor as a plain ASCII `>` (not `❯`/`›`/`▶`), so a menu like "Pick next move? > 1. … 2. … 3. …" had `sawArrow=false` and was mis-read as a finished turn (fired "Agent finished" + the configured action over a live prompt). Two additions: (a) `sawArrow` is now also set when a line matches `^>\s+\d+[\.\)]\s` (a `>` cursor sitting directly on a numbered option — conservative so a stray `>` in prose or the input line `> /model …` isn't counted), and `>` is added to the numbered-item cursor class; (b) the selection-menu footer strings `esc to cancel` / `enter to select` / `to navigate` (from Claude Code's "Enter to select · ↑/↓ to navigate · Esc to cancel" line) were added to `AgentPromptKeywords` — highly menu-specific, so they suppress the false completion even when the cursor glyph isn't recognized. `to navigate` arrow-gated (v80.0): bare `to navigate` also matches ordinary prose in a finished answer ("added a sidebar to navigate between pages"), which mis-classified the settled turn as a waiting menu and silently suppressed the notification — it now only counts when the same line also contains an `↑`/`↓` arrow glyph (which Claude Code's real footer always renders next to the phrase); `esc to cancel`/`enter to select` stay as plain keywords. Input-reply backoff (v14.0, reworked in v18.0): while `_awaitingAgentInputReply` is set, the capture must not fight the user as they answer — each `AttachConsole`/`FreeConsole` on VS bounces the embedded conhost's keyboard focus, which is what made arrow keys/typed answers to agent menus unreliable. v14.0 backed off from 1 s to `InputPromptRecheckMs` (10 s) but only `&& IsTerminalFocused()` — exactly wrong, because while the user clicked *into* an unfocused terminal to answer, the 1 s attach storm kept knocking focus back out (they had to click the panel and the agent tab repeatedly). v18.0 splits on focus the other way: focused → never attach (nothing to detect until the user acts, and a focused user can see the result, so a delayed finish notification costs nothing — this is what keeps a poll from knocking focus out mid-reply); unfocused → attach but only every 10 s (so a user clicking in isn't fought by a rapid storm, while an agent that resumes on its own is still noticed within ~10 s). Once unfocused-and-read shows the screen no longer looks like a prompt (user answered → agent working), `_awaitingAgentInputReply` clears and the normal 1 s cadence resumes. Sticky waiting + early classification (v15.0): the prompt classification now runs as soon as the settled screen holds still for one tick (before the full idle window), so the menu backs off the cadence within ~1 s of appearing instead of after `IdleSeconds`; and on a hash change `_awaitingAgentInputReply` is re-evaluated as `LooksLikeAgentInputPrompt(text)` rather than unconditionally cleared. Arrow-keying a selection menu moves the `❯` cursor and so changes the screen — clearing the flag on every such change dropped the cadence back to 1 s mid-navigation and the next attach ate the arrow keys (reported in plan mode). Keeping the flag set while the changed screen still looks like a prompt holds the 10 s cadence throughout navigation; it clears (resuming 1 s) only once the screen no longer looks like a prompt (user answered → agent working). Typing-interference guard: the capture briefly attaches VS (disturbs keystrokes), so each tick skips the read while the user is *actively typing* — gated on a recent terminal keystroke (`_lastTerminalKeyUtc`, within `TerminalTypingGuardMs`=1500) and `IsTerminalFocused()`. Mere focus isn't enough (pasting leaves the terminal focused but un-typed — a focus-only gate stalled the turn ~15s). Prompt-typing guard (v27.0): the tick also skips while the user recently typed in the WPF prompt box (`_lastPromptKeyUtc`, set in `PromptTextBox_PreviewKeyDown`, within the same window) — the attach was bouncing keyboard focus out of the prompt mid-keystroke during active generation ("sometimes I can't type while the agent works"). No focus check needed here: a recent prompt keystroke already proves the user is in the prompt, and 1.5s after they stop, detection resumes. Focus-restore around the read (v30.0): the typing guards only pause the poll while the user is *actively* typing (a keystroke within `TerminalTypingGuardMs`). When the user pauses longer than that, the next tick's `AttachConsole`/`FreeConsole` still bounces native keyboard focus off the embedded terminal (or the WPF prompt), and the now-unfocused terminal swallows the next keystroke — which, because it never reaches the terminal, can't refresh `_lastTerminalKeyUtc` to re-arm the guard, so the poll keeps stealing focus every second and the terminal stays dead for the rest of the turn (the recurring "console stops accepting keyboard input after a while", reported with OAF enabled on Command Prompt). The tick now snapshots `GetFocus()` immediately before the `Task.Run` read and, if it was one of our input surfaces (`IsOwnedInputFocusWindow()` — the terminal/its child, or the WPF `HwndSource` host), restores it with `SetFocus` right after the read when it moved. Captured on the UI thread (joined to the terminal's input queue via SetParent, so `GetFocus`/`SetFocus` see the terminal the same way the focus guards do); restore runs before any of the post-read early-returns so every read path is covered. Makes the poll focus-neutral rather than relying solely on the active-typing skip. Selection-freeze guard (v34.0): clicking or marking text in a QuickEdit conhost puts it into selection/mark mode, which freezes the screen buffer — the agent keeps working but the captured text stops changing, so the watcher read a static screen and fired a premature "finished" notification the moment the user clicked into the terminal mid-turn (issue #94). Each capture now calls `GetConsoleSelectionInfo` while attached and sets `_consoleSelectionActive` when `CONSOLE_SELECTION_IN_PROGRESS`/`CONSOLE_SELECTION_NOT_EMPTY`/`CONSOLE_MOUSE_DOWN` is set; the tick treats that as activity (pushes `_lastConsoleChangeUtc` forward and returns without firing), so detection resumes only once the user clears the selection and conhost unfreezes the buffer. Background-agents suppression (v55.0): Claude Code parks the main turn while its own background/sub-agents run, showing a static "✳ Waiting for N background agents to finish" status line. That screen holds still, so the watcher read it as idle and fired a premature "Agent finished" notification (+ any configured action) while the turn was really still in progress ("On Agent Finish doesn't apply with background agents"). `LooksLikeWaitingForBackgroundAgents(text)` (regex `waiting for \d+ background agents? to finish`, kept specific to Claude Code's exact wording so a finished turn's prose can't match) is checked in the settle branch of `EvaluateScreenQuiescenceAsync` before the idle-window/fire logic; on a match the tick treats it as activity (pushes `_lastConsoleChangeUtc` forward and returns without firing), so the notification only fires once the background agents finish, the screen changes to the final answer, and it settles normally. Question sound (v52.0): `AgentFinishConfig.PlayQuestionSound` (opt-in, independent of `PlaySound`) plays a distinct descending tone (`PlayQuestionSound()`, C6→G5→D5) when the agent parks at a prompt instead of finishing, so "the agent needs me" is audibly distinct from the rising finish chime. Fired via `MaybePlayQuestionSound()` from `EvaluateScreenQuiescenceAsync` — at the false→true transition in the hash-changed branch and again in the settle branch — guarded by `_questionSoundPlayed` so it sounds once per waiting episode; the guard clears when a later screen no longer looks like a prompt (agent resumed), so the next question sounds again. Reset (with `_awaitingAgentInputReply`) on each arm
- Focused-generation throttle (v59.0): after the typing guards, the conhost tick returns early when the screen changed within the last 3s and `IsTerminalFocused()` — throttling captures from 1s to ~3s while the user keeps the terminal focused during active output. Rationale: each `AttachConsole` can bounce the conhost's keyboard focus, and every bounce feeds a FOCUS_EVENT into the agent's stdin that triggers a TUI re-render; with a very long turn on screen (plan mode) re-renders are expensive on Windows and the per-second bounce storm helps starve the agent's input loop right when it asks its question (issue #89). The gate deliberately does not push `_lastConsoleChangeUtc` forward (that would keep it closed forever): once output stops, the 3s window lapses, captures resume at 1s and the idle countdown (≥5s) still starts on time. Distinct semantics from the typing guard above it (which does push the idle window forward)
- Modal-dialog guard (v29.0, hang fix): `OnAgentCompletionTimerTick` skips the entire tick when `System.Windows.Interop.ComponentDispatcher.IsThreadModal` is true (and pushes `_lastConsoleChangeUtc` forward so the turn is detected as finished only after the dialog closes). The watcher rides a `DispatcherTimer`, which keeps ticking inside the nested modal message loop that an open WPF dialog pumps — so with a turn settling while the consolidated Settings dialog (or the On-Agent-Finish config sub-dialog, or a `MessageBox`) was open, the tick ran the process-global `AttachConsole`/`FreeConsole` read and could fire the action (`dte.ExecuteCommand("Debug.Start"/"Build…")`) or add the info bar to the modally-disabled main window from underneath that loop, deadlocking Visual Studio. `IsThreadModal` is true on the UI thread for any WPF modal, so the single check covers every dialog with no per-call-site wiring
- Notify: `OnAgentTurnCompletedAsync` plays a chime (opt-in) and shows a VS main-window info bar (`ShowAgentFinishNotificationAsync` via `__VSSPROPID7.VSSPROPID_MainWindowInfoBarHost` + `SVsInfoBarUIFactory`) reading `Agent finished · <duration>` (+`<Δtokens>` only for Claude), shown even when the tool window is hidden. `AgentFinishInfoBarEvents` (`IVsInfoBarUIEvents`) handles close/unadvise and the action hyperlink
- Actions (`ExecuteMainActionAsync`, returns `bool` success): Build/Rebuild → `BuildAndCheckSuccessAsync()` (`dte.ExecuteCommand` + `WaitForDteBuildToFinishAsync` + `SolutionBuild.LastBuildInfo` — false on timeout or a failed project); Run/RunWithoutDebugging → `PrepareAndRunAsync()` (also returns `bool`: false if the clean/rebuild gate failed or timed out, otherwise true after issuing `Debug.Start`/`Debug.StartWithoutDebugging`); RunTests → `dte.ExecuteCommand("TestExplorer.RunAllTests")` (fire-and-forget, always true — no completion signal available); RunScript → `RunFinishScriptAsync` `Process.Start` (`UseShellExecute`) in the workspace dir, always true (fire-and-forget) — a `.cmd`/`.bat` is wrapped as `cmd.exe /k "<path>"` and a `.ps1` as `powershell.exe -ExecutionPolicy Bypass -NoExit -File "<path>"` (the `.ps1` default shell verb is Edit, so shell-executing it directly would open an editor; `/k`/`-NoExit` keep the console open for output), anything else is shell-executed directly; SendToAgent → `SendTextToAgentAsync` (terminal paste, or the structured channel under native mode — see *Native Mode*), always true. `RequireFileChanges` gates on `git status --porcelain` in `_gitRepositoryRoot` (non-git ⇒ never blocks); the change check runs before the chime/info-bar in `OnAgentTurnCompletedAsync`, so when the action is skipped for lack of changes the turn is fully silent (no sound, no notification) rather than announcing the skip. `Confirm` (default true) surfaces the action as an info-bar button instead of auto-running
- Follow-up ("also send to agent"): `AgentFinishConfig.FollowUpSendToAgent` (optional) sends a second literal text to the agent — e.g. "Commit and push the changes" — after `Action` succeeds. `HasFollowUp()` gates it on a non-empty value and `Action` being neither `None` (nothing ran) nor `SendToAgent` (already sends text itself; a second send has no success signal to key off and could race the agent's own next turn). UI field in `ShowAgentFinishSettingsDialogAsync` is enabled/disabled per-action via `SyncFollowUpOptions()`. Non-confirm path: `ExecuteAgentFinishActionAsync()` runs `ExecuteMainActionAsync` then, only if it returned true, sends the follow-up — one uninterrupted auto-run. Confirm path: `OnAgentTurnCompletedAsync` does not chain the follow-up behind the main action's button — it shows a first info bar/button for the main action, and only after that's clicked and `ExecuteMainActionAsync` returns true does it show a second, separate info bar/button (`DescribeSendCommand`-labeled) for the follow-up, so a build failure (or a declined/skipped action) never silently triggers the commit-and-push step. Presets (v50.0): a "Preset ▾" `Button` + `ContextMenu` next to the follow-up `TextBox` (`FollowUpPresets`, an array of `(label, text)` tuples in AgentFinishDialog.cs) lets the user fill the field from canned text instead of typing it — currently a plain "Commit and push the changes" and a "no AI credit" variant that asks the agent to keep only the human author and drop AI references from the commit. Picking an item overwrites the field (a follow-up is a single message, not something to append to). Add more entries to `FollowUpPresets` to offer more canned follow-ups
- Notification label length (v50.0): `DescribeSendCommand()` (used for both the `SendToAgent` action's button label and the follow-up's second-notification label) truncates at `SendCommandLabelMaxChars` (100, was 24) — the VS info-bar hyperlink can render much more than a button-sized label, and 24 chars cut off canned follow-ups like the presets above well before the meaningful part
- Console interop (Interop.cs): reuses `AttachConsole`/`FreeConsole`/`CloseHandle`/`COORD`; adds `CreateFile`, `GetConsoleScreenBufferInfo`, `ReadConsoleOutputCharacterW`, `SetConsoleCtrlHandler`, `Beep`, and `SMALL_RECT`/`CONSOLE_SCREEN_BUFFER_INFO`; `GetConsoleMode` + `ENABLE_QUICK_EDIT_MODE` (0x40) back `IsTerminalInMouseInputMode()`, the paste/zoom QuickEdit probe for issue #76/#78 (reads CONIN$ mode under the same guarded attach as the screen capture); `GetConsoleSelectionInfo` + `CONSOLE_SELECTION_INFO` back the v34.0 selection-freeze guard (issue #94 — see Completion detection above); `GetCurrentConsoleFontEx`/`SetCurrentConsoleFontEx` + `CONSOLE_FONT_INFOEX` back `TryAdjustConhostFontSize()` (changes the conhost cell height on CONOUT$ for the input-mode-independent Ctrl+Scroll zoom, issue #78)

## Auto-Send Build Errors (BuildErrors.cs)

- Opt-in: gated by `_settings.AutoSendBuildErrorsToAgent` (default false; toggled on the Settings → Behavior tab). The build-event subscription itself is always established at load — the setting is only checked at fire time, so toggling it doesn't require re-subscribing
- Subscription lifetime: `InitializeBuildErrorAutoSend()` (called from `ClaudeCodeControl_Loaded`, idempotent via the `_buildEvents != null` guard since Loaded re-fires on tab switches) grabs `dte.Events.BuildEvents` and stores it in the `_buildEvents` field — DTE event sink objects are collectible, so dropping the reference would silently unsubscribe. `DisposeBuildErrorAutoSend()` unsubscribes in `CleanupResources()`
- Trigger: `OnBuildDone(scope, action)` fires on the UI thread after any build. It acts only on `vsBuildActionBuild` / `vsBuildActionRebuildAll` (Clean/Deploy ignored), only when the setting is on, and only when no send is already in flight (`_autoSendBuildErrorsInProgress`). The real work runs fire-and-forget via `HandleBuildDoneAndMaybeSendAsync`
- Error List read: `TryCollectBuildErrors` casts the DTE to `EnvDTE80.DTE2` and reads `ToolWindows.ErrorList.ErrorItems` (1-based). `vsBuildErrorLevelHigh` → errors, `vsBuildErrorLevelMedium` → warnings; lower levels ignored. A 250 ms delay after `OnBuildDone` lets the Error List finish populating before the read. Each item is formatted as `relPath(line,col): description` with a solution-relative, forward-slash path (`MakeSolutionRelativePath`, portable across native/WSL agents); file-less items fall back to just the description
- Send conditions: only sends when there is ≥1 error (warnings-only builds don't fire — matches "when it shows errors"; warnings ride along as context) and an agent terminal is live (`terminalHandle`/`IsWindow`). No terminal ⇒ skip silently
- Loop/spam guard (important): `_lastAutoSentBuildErrorSignature` holds the newline-joined error set of the last send; an identical set is skipped so an "On Agent Finish → Build" cycle where the agent makes no progress can't spam the terminal forever. A build that produces zero errors clears the signature, so a later identical failure (fixed then reintroduced) is sent again
- Prompt: `FormatBuildErrorPrompt` writes a summary line + numbered Errors list (cap 40) and, when present, a Warnings list (cap 20), each with an "... and N more" tail, ending with a "rebuild to confirm" instruction. Delivered through `SendTextToAgentAsync` (the normal paste path, or the structured channel under native mode — see *Native Mode*)
- Manual send (v68.0): `SendBuildErrorsButton_Click` is a `ToolbarButton.SendBuildErrors` configurable feature (see *Cross-Cutting Rules* / SettingsDialog "Toolbar" tab) that collects the current Error List and sends it to the running agent on demand, bypassing `AutoSendBuildErrorsToAgent` entirely — it works whether the setting is on or off. It reuses `TryCollectBuildErrors`/`FormatBuildErrorPrompt`, shows a `MessageBox` when there are no errors or no running terminal (instead of failing silently like the auto path), and updates `_lastAutoSentBuildErrorSignature` so an auto-send right after a manual send doesn't immediately re-fire on an unchanged error set
- Large-prompt delivery (v68.0): both send paths go through `SendBuildErrorPromptAsync` rather than calling `SendTextToTerminalAsync` directly. A handful of errors with full relative paths easily clears ~1 KB, and a raw clipboard paste that large risked leaving the CLI's bracketed-paste state stuck mid-transfer (terminal shows "Pasting..." forever, nothing arrives) — the same failure mode `SendLargePromptsAsFile` exists to avoid for the prompt box (`LargePromptThresholdChars` in UserInput.cs). Since this text is generated, not typed, `SendBuildErrorPromptAsync` applies the file-reference trick unconditionally above `LargeBuildErrorPromptThresholdChars` (1024 chars, same threshold) regardless of the user's `SendLargePromptsAsFile` toggle: writes the prompt to a temp `.md` under `%TEMP%\ClaudeCodeVS_Session\<guid>\`, WSL-path-converts it for WSL providers, and sends `"Read and follow: <path>"` instead of the raw text
- `async void` click handler, not `JoinableTaskFactory.Run` (v68.0): `SendBuildErrorsButton_Click` is a plain `async void` handler, matching `CustomCommandMenuItem_Click`. An earlier version wrapped the body in a blocking `ThreadHelper.JoinableTaskFactory.Run(async () => ...)` (matching `ViewChangesButton_Click`'s pattern) and worked under Command Prompt but silently sent nothing under Windows Terminal. Root cause: WT's paste goes through `PasteViaCtrlShiftVAsync` — a foreground-focus-stealing `keybd_event` Ctrl+Shift+V that depends on `FocusTerminalForInputAsync` actually landing real OS foreground focus — and running that inside `JoinableTaskFactory.Run`'s nested/reentrant message pump disrupted that focus/activation timing. Command Prompt's paste (`PasteViaConhostPasteCommandAsync`) is a handle-targeted `PostMessage`, which doesn't depend on foreground focus and so wasn't affected. Any new click handler that ends up calling `SendTextToTerminalAsync`/`SendBuildErrorPromptAsync` should use `async void` (or otherwise avoid a blocking `JoinableTaskFactory.Run` around the send), not the `ViewChangesButton_Click`-style wrapper
- Arms "On Agent Finish" (v68.0): `SendBuildErrorPromptAsync` calls `ArmAgentCompletionWatcherAsync()` right after `SendTextToAgentAsync`, for both the auto-send and manual-button paths — skipped under native mode (`IsNativeModeActive`), where the turn ends on a protocol event that arms itself. That watcher is normally armed only by `SendButton_Click` (see *On Agent Finish* below) — a build-error send bypasses the prompt box entirely, so without this explicit call the "On Agent Finish" notify/action configured by the user would never fire after the agent responds to a build-error fix request

## Auto-Send Runtime Errors (RuntimeErrors.cs, #110, v76.0)

- Sibling of Auto-Send Build Errors, but debugger-driven: build errors come from the Error List at build time; runtime exceptions only surface through the debugger, so this hooks `dte.Events.DebuggerEvents` instead of `BuildEvents`. Opt-in via `_settings.AutoSendRuntimeErrorsToAgent` (default false, Settings → Behavior tab, right below the build-errors checkbox)
- Subscription lifetime: `InitializeRuntimeErrorAutoSend()` (called from `ClaudeCodeControl_Loaded` right after `InitializeBuildErrorAutoSend()`, idempotent via the `_debuggerEvents != null` guard) stores the sink in the `_debuggerEvents` field for the same GC reason as `_buildEvents`. `DisposeRuntimeErrorAutoSend()` unsubscribes in `CleanupResources()`
- Trigger — unhandled only: `OnDebuggerEnterBreakMode(reason, ref action)` fires on the UI thread on every break, but acts only on `dbgEventReasonExceptionNotHandled`. First-chance/handled exceptions (`dbgEventReasonExceptionThrown`), breakpoints, and steps are ignored — forwarding every caught exception would be far too noisy
- Reads `$exception` while paused: the exception is only readable during break mode, so `TryCollectRuntimeException` runs synchronously inside the handler (not fire-and-forget). It evaluates `$exception.ToString()` / `.GetType().FullName` / `.Message` via `dte.Debugger.GetExpression(expr, false, 2000)`, unwrapping the debugger's quoted/escaped string form (`UnwrapDebuggerString`). Falls back to `CurrentThread.StackFrames` function names (`TryCollectCallStack`, cap 25) when `ToString()` yields no stack
- Spam guard: `_lastAutoSentRuntimeErrorSignature` holds the last-sent details; an identical exception breaking again back-to-back is skipped. `_autoSendRuntimeErrorsInProgress` prevents overlapping sends. Skips silently when no agent terminal is live (`terminalHandle`/`IsWindow`)
- Delivery: `SendRuntimeErrorPromptAsync` reuses the build-error large-prompt trick — text over `LargeBuildErrorPromptThresholdChars` (1024) is written to a temp `.md` and sent as `"Read and follow: <path>"` (WSL-path-converted for WSL providers), otherwise sent inline via `SendTextToAgentAsync`. Arms `ArmAgentCompletionWatcherAsync()` afterward (skipped under native mode), same as the build-error path

## Debug Visibility (DebugVisibility.cs, #130, v131.0)

- Problem: VS's own tool-window layout/auto-hide behavior can hide the Claude Code panel (and any tab it spun off) while the user's project runs under the debugger, leaving them unable to type into it (issue #130)
- Always on, not opt-in: unlike Auto-Send Build/Runtime Errors, there is no setting — staying visible while debugging isn't something a user would opt out of
- Subscription lifetime: `InitializeDebugVisibility()` (called from `ClaudeCodeControl_Loaded`, idempotent via the `_debugVisibilityEvents != null` guard) grabs `dte.Events.DebuggerEvents` into the `_debugVisibilityEvents` field, same GC-collectible-sink reason as `_buildEvents`/`_debuggerEvents`. `DisposeDebugVisibility()` unsubscribes in `CleanupResources()`
- Trigger: `OnDebugEnterRunMode(reason)` fires on `OnEnterRunMode` — every time the debuggee starts or resumes running (F5, Continue after a breakpoint) — and fires-and-forgets `ShowExtensionAndCreatedTabsAsync()`
- What gets shown: the main `ClaudeCodeToolWindow` (created via `FindToolWindow(..., create: true)` if not already open — it should always be available while debugging), the detached terminal tab if `_isTerminalDetached`, the default native-mode chat tab (`_nativeChatWindow`), and every parallel chat session's tab (`_nativeSessions[...].Window`)
- `ShowNoActivate`, not `Show`: the issue is about visibility, not focus — using `Show()` would yank keyboard focus away from the user's editor on every single Continue press while stepping through code. `ShowNoActivate()` restores visibility (undoes VS auto-hide collapsing the pane) without stealing focus, same rationale as the Claude usage tab's auto-restore (see *Claude Usage*)

## "@" File/Folder Picker (AtMention.cs)

- Two targets, one index (v93.0): the popup logic is generalized over a private `AtMentionTarget` (text box + its own `Popup`/`ListBox`/`MentionStart`/`SuppressTextChanged`) so the terminal-mode `PromptTextBox` and the native chat composer (`ChatTranscript.ComposerInputBox`) each get an independent popup instance (`GetAtMentionPanelTarget()` / `GetAtMentionComposerTarget()`, lazily created) without fighting over which box the popup is anchored to. Always on; no setting
- Index: `EnumerateWorkspaceEntries()` walks `GetWorkspaceDirectoryAsync()` on a background thread, skipping build/VCS/package dirs (`AtIgnoredDirs`) and reparse points, returning workspace-relative `/`-separated paths (folders carry a trailing `/`), capped at 8000. Cached per-root with a 30 s TTL (`EnsureAtEntriesAsync`); a stale index refreshes in the background while current results still show. First trigger shows an "Indexing…" row, then `EnsureThenRefilterAsync` re-runs the filter
- Popup: a programmatic `Popup` + `ListBox` per target (`EnsureAtPopup(target)`), positioned at the caret via `GetRectFromCharacterIndex`. Themed with `GetThemeBrushes` + a derived hover brush (`ComputeAtHoverBrush`) so selected/hover rows stay readable in a standalone popup (no system-blue). - Ranking (`RankAtEntries`): a query may contain `/` for folder drill-down — the part after the last `/` matches the entry name and the prefix constrains the subtree; name prefix-matches rank above name/path substring matches
- Insert (`CommitAtSelection`): replaces the typed `@query` with `@<relative-path>`; a file appends a space and closes, a folder leaves the caret in place and re-opens the picker to drill in. Relative paths resolve for every provider (terminal cwd = workspace), so no WSL conversion. `target.SuppressTextChanged` guards the programmatic edit
- Composer exposure: `ChatTranscriptView` exposes `ComposerInputBox` (the raw `TextBox`, same pattern as the pre-existing `ComposerAttachmentsPanel`) since the popup needs direct caret/selection/character-rect access that its higher-level `ComposerText`/`SetComposerText` API doesn't offer

## Native Mode — Agent Sessions (Agents/, NativeMode.cs, UI/ChatTranscriptView.xaml, v82.0)

Opt-in alternative to the embedded terminal: the panel renders the conversation as a WPF chat and talks to the CLI over its headless JSON protocol instead of screen-scraping a console. Gated by `_settings.UseNativeMode` (single global bool, default false, Settings → Terminal tab); changing it restarts the agent like a terminal-type change.

- Why a protocol and not a hidden `cmd.exe`: plain stdio redirection does *not* work — these CLIs are TUI apps that detect the missing TTY and either refuse interactive mode or emit raw ANSI. Every supported provider instead exposes a documented headless mode, which is what the adapters drive.
- `Agents/` has no WPF and no VS SDK reference — deliberate, so the parsers are unit-testable with no process and no running Visual Studio (`Tests/AgentStreamParsingTests.cs`).

### Contract and event model

- `Agents/IAgentSession.cs`: `StartAsync(workingDir, ct)`, `SendAsync(text)`, `InterruptAsync()`, `DisposeAsync()`, event `Received`, plus `SessionId` / `Model` / `SupportsInterrupt`.
- `Agents/AgentEvent.cs`: one flat class (not a hierarchy — adapters stay allocation-cheap and the UI switches on `Kind`) with `AgentEventKind` = `SessionStarted`, `AssistantText`, `Thinking`, `ToolCallStarted`, `ToolCallCompleted`, `PermissionRequested`, `TurnCompleted`, `UsageUpdated` (mid-turn token counts for the live status line — see *Live turn clock*), `RateLimitUpdated`, `SessionError`. Payload types: `AgentUsage`, `AgentPermissionDenial`, `AgentPermissionRequest` (answer-once, `Respond`/`Cancel` guarded by a lock so a double-click can't corrupt the JSON-RPC exchange), `AgentRateLimit`.
- `SessionStarted` is per turn, not per conversation (measured with Claude: the tool list can even grow between turns as skills load). Clearing the transcript on it would wipe the history on the second prompt — treat it as "here is the current inventory".

### `Agents/JsonLineProcessHost.cs` — the shared plumbing

`Process.Start` with all three streams redirected, `CreateNoWindow`, UTF-8 without BOM, line-oriented reader task, writes serialized by `SemaphoreSlim`, teardown that kills the whole tree (`Agents/ProcessTree.cs`, extracted from Terminal.cs rather than duplicated). Five things that bite and are handled here:

1. stdin stays open between turns — closing the pipe ends the session (observed: the process exits right after the `result`).
2. stderr is drained in parallel — otherwise the buffer fills and the child blocks.
3. No fixed line buffer — a single JSON line routinely passes 100 KB (thinking blocks carry a signature).
4. Every event reaches the UI through `SwitchToMainThreadAsync()` — the reader runs on a thread-pool thread.
5. stdin is written through an own UTF-8 `StreamWriter` over `StandardInput.BaseStream`, never through `Process.StandardInput` (v89.0). `ProcessStartInfo.StandardInputEncoding` does not exist in .NET Framework (it arrived in .NET Core 2.1), and the writer the framework builds encodes in `Console.InputEncoding` — the machine's ANSI/OEM code page, since Visual Studio has no console. `StandardOutputEncoding`/`StandardErrorEncoding` were set from the start, so only the *inbound* half was wrong and it stayed invisible for ASCII prompts. Every CLI here reads stdin as UTF-8: measured, a prompt of `olá Codex` went out with `á` as one code-page byte and `codex exec -` answered *"input is not valid UTF-8 (invalid byte at offset 2)"* on stderr and exited 1 in ~1.3 s, before `thread.started` — which surfaced as the bare "Codex exited with code 1 without finishing the turn." The same corruption applied to every adapter (the Claude/ACP/PI JSON payloads carry the prompt text raw — Newtonsoft does not escape non-ASCII by default), so the fix belongs here rather than in any one adapter. `CloseInput()` and `Dispose()` close *that* writer, which flushes it before the pipe goes.

- Devin's model is a session config option, not a launch flag (v102.0): `devin acp` accepts no `--model` (the global flag exists only for the TUI/print modes), and the agent instead publishes `configOptions: [{id:"mode"…},{id:"model", type:"select", currentValue, options:[{value:"claude-opus-4-8-high", name:"Claude Opus 4.8 High"}…]}]` on `session/new`, changed with `session/set_config_option {sessionId, configId, value}` — `configId`, not `optionId`, and `session/set_model` does not exist there (`-32601`). A model the agent does not list raises a `SessionError` row at launch rather than being dropped silently — a stale entry in the user's list is exactly how the original bug went unnoticed. OpenCode publishes the same option and reuses this path; Reasonix publishes none (see the next bullet).
- Every other adapter carries the model too (v111.0): `GetAcpModelName` returns the provider's saved pick for OpenCode/Devin, `CreateOneShotSession`/`CreatePiSession`/`CreatePrintModeSession` fill `Model` for Codex/Cursor/PI/Antigravity, and Reasonix — which answers `session/new` with no `configOptions` at all, so there is nothing to set — gets `AcpSessionOptions.ModelLaunchArgument = "-m <id>"`, appended to the `acp` subcommand by `AcpCommandBuilder`. Only the ACP config option can switch a *running* session; everything else needs the relaunch `OnChatProviderModelSelected` offers. Cursor is asked for `auto` when nothing is picked, because a free plan refuses every named model. See *Model Catalog & Selection* for where the lists come from.
- Reasonix's first-ever launch blocks on a console prompt with no trailing newline (v116.0): on a machine that has never run `reasonix` before, the CLI prints `Allow anonymous CLI usage statistics? [Y/n]:` and waits on stdin — before the ACP server starts, and without a trailing `\n`. `JsonLineProcessHost.PumpAsync` reads with `StreamReader.ReadLineAsync()`, which never returns for a line that never ends, so `initialize` hung forever with no line ever reaching `OnLineReceived` to react to (reported: native Reasonix "not working", the terminal-mode equivalent never had this because interactive typing answers the prompt without anyone noticing it was there). `AcpSessionOptions.AnswerFirstRunPromptWithNo` (set for Reasonix in `CreateAcpSession`) makes `AcpSession.StartAsync` run `PrimeFirstRunPromptAsync` first: a disposable copy of the same command is launched, fed `"n\n"` on stdin the instant it starts, and killed after a 1.5s grace period. When the prompt exists this answers it and the CLI persists the choice to its own config, so the real session started right after never sees it again. When the prompt does not exist (already answered on a prior run) the extra `"n\n"` lands on an already-running ACP server's stdin as one line it cannot parse as JSON-RPC — the same case `OnLineReceived` already tolerates from the other direction — and the 1.5s is spent either way since `acp` mode never exits on its own.
- The priming process's kill did not wait for the OS to actually finish tearing it down (v120.0): `PrimeFirstRunPromptAsync`'s `finally` block called `ProcessTree.Kill(process.Id)` and returned immediately — `Kill()` only requests termination, it does not block until the process is gone. Hardened by awaiting `WaitForExitAsync(process)` (bounded to 2s) right after the kill, so the primer is confirmed gone before the real session's process starts.
- The primer-teardown race theory (v120.0) — shipped, then refuted; do not re-derive it: v120.0 added an unconditional `Task.Delay(400)` at the end of `PrimeFirstRunPromptAsync` on the theory that the real session was racing a workspace-scoped lock the primer had not finished releasing. It did not fix anything, and the theory is now disproved on three counts, all measured: (a) the delay demonstrably ran — `terminal-launch.log` failure timings moved from ~385-479ms to ~816-853ms, exactly +400ms — and the start still failed; (b) driving this exact `AcpSession` from the built DLL *outside* `devenv.exe` starts Reasonix reliably in ~1s with zero delay, primer included (`SessionId` returned, `Model = reasonix v1.18.0`); (c) two Reasonix ACP sessions launched simultaneously against the same workspace both handshake fine, so there is no such lock. The earlier orphaned-process explanation is dead too: `Get-Process reasonix` returns nothing while the bug reproduces. The delay is kept only as cheap insurance for the OS-teardown window and is documented as such in the code — it is not the fix for anything, and it is not evidence that a race exists. What *is* established: the child dies immediately after launch and the first `initialize` write lands on a broken pipe (`InvalidOperationException: Agent process closed its input pipe`), `TryStartNativeModeAsync` catches it and falls back to the terminal, and this happens only inside `devenv.exe` — not reproducible externally. Unexplored leads: `session.StartAsync` runs on the VS UI thread after `SwitchToMainThreadAsync()`, and `EnsureNoConsoleAttached()`'s `AttachConsole`/`FreeConsole` std-handle juggling runs immediately before the launch (the same std-handle state that caused #73). The v121.0 diagnostics below exist to settle it from a real failing run.
- ROOT CAUSE, found by the v121.0 diagnostics: the Reasonix model flag was `-m`, and `acp` only accepts `-model` (v122.0): `GetAcpModelLaunchArgument` built `-m <id>`, so the launch line was `reasonix.cmd acp -m deepseek-chat`. The `acp` subcommand parses its own flags with Go's `flag` package, which does no prefix matching — it printed `flag provided but not defined: -m` plus its usage block to stderr and exited with code 2 before the ACP server started, so the first `initialize` write hit an already-dead pipe. That is the whole bug: every failure traced back to it, and the two earlier explanations (orphaned process, primer teardown race) were wrong. It never reproduced outside `devenv.exe` only because the external probes passed no model at all — with no model the flag is empty and Reasonix starts fine, which is also why terminal mode was unaffected (it switches models with `/model <id>` inside the TUI, never on the command line). Fix: `-model <id>`. The flag is now built by `AcpCommandBuilder.BuildReasonixModelArgument` rather than inline in the control — `GetAcpModelLaunchArgument` lives on `ClaudeCodeControl`, which the unit suite cannot load (WPF + VS SDK), so nothing could cover it; moving the one string into the pure builder is what lets `ModelCatalogTests` pin the spelling.
- …and the model list it was picked from was wrong too (v123.0): with `-model` accepted, the launch got one step further and died at `session/new: unknown model "deepseek-chat"`. Reasonix's `--model` takes a provider name from the user's `config.toml`, and the extension was offering a hard-coded list of DeepSeek *model ids* — no entry in it was ever valid, so every native Reasonix launch with a model selected failed, on any machine. The list now comes from `reasonix doctor --json` like every other discovered catalog (see *Model Catalog & Selection*), and `DropRetiredReasonixModelSelection` clears the stale pick on upgrade before it can break a launch. Two bugs stacked on the same feature is why v122.0 alone did not fix it: the flag had to be right before the value error could even surface.
- ACP start failures now report the agent's own last words (v121.0): `AcpSession` keeps a `_stderrTail` ring buffer (`StderrTailLines` = 8, `StderrExcerptLength` = 800 — same trick and same caps as `OneShotResumeSession`) and an optional `AcpSessionOptions.DiagnosticLog` sink, wired by `CreateAcpSession` to `LogTerminalLaunch` so everything lands in `%LocalAppData%\ClaudeCodeExtension\terminal-launch.log`. Logged: the resolved launch command (`file`/`args`/`cwd`/`priming`), the primer's fate (self-exited with its exit code and stderr, or killed with whether the kill was confirmed), the real child's pid, and on failure `start FAILED:` with the child's exit code, the pending-request count and the stderr tail. `DescribeStartFailure` wraps the raw pipe `IOException` into a message that names the agent and quotes that stderr, so the info bar says something usable too. Two details matter: the failure path awaits `_host.WaitForOutputDrainAsync(1000)` before reading the tail — the write fails the *instant* the pipe breaks, which is before the stderr pump has surfaced the dying process's last lines — and `Log()` swallows sink exceptions, since a caller-supplied sink must never be what fails a session. Covered by `Tests/AcpStartDiagnosticsTests.cs`, which drives real throwaway `.cmd` children (a process that actually dies is the whole point; mocks reproduce none of it).
- Switching provider from the ⚙ menu skipped native mode entirely (v118.0): the 12 `<Provider>MenuItem_Click` handlers in `ProviderManagement.cs` (`ClaudeCodeMenuItem_Click`, `ReasonixMenuItem_Click`, etc. — the actual "Claude Code / Codex / Cursor Agent / …" provider list under ⚙) predate native mode and were never updated when it landed (v82.0): each one sets `_settings.SelectedProvider` and then calls `StartEmbeddedTerminalAsync(provider)` directly, which launches the console terminal unconditionally and never calls `TryStartNativeModeAsync`. Only `InitializeTerminalAsync` (extension/solution load) and `RestartTerminalWithSelectedProviderAsync` (the Restart button) checked native mode, so a provider picked from that menu always ran in the terminal regardless of `UseNativeMode` — and every *later* menu pick did too, since nothing about the mechanism changes between providers. Reported as "Reasonix native isn't working, and after that other providers stay on the terminal too": the user's actual repro was switching to Reasonix from that menu (hitting the bug), then switching away to other providers from the same menu (hitting it again) — nothing Reasonix-specific was needed to reproduce it for any provider. Fix: each handler's available-provider branch now tries `TryStartNativeModeAsync()` first (it reads `_settings.SelectedProvider`, already set above) and only falls through to `StartEmbeddedTerminalAsync` when that returns false, matching the startup/restart paths. The unavailable-provider branch (`ShowXInstallationInstructions` + plain CMD) is untouched — nothing there needs a structured channel
- Diagnostic logging for native-mode start failures (v119.0): `TryStartNativeModeAsync` previously only reported failures via `Debug.WriteLine` (invisible without a debugger attached) and the easy-to-miss info bar (no exception detail). It now also writes to the same `%LocalAppData%\ClaudeCodeExtension\terminal-launch.log` used by the terminal launch path (`LogTerminalLaunch`, reused from `Terminal.cs` — same partial class), logging the attempted provider, which of the three fallback branches fired (unsupported provider / no workspace / exception, the exception logged with full `ToString()` including inner exceptions and stack trace), and a success line when the session starts — so a user hitting a silent fallback can be asked for this file instead of needing to reproduce under a debugger
- A failed one-shot turn quotes stderr (v89.0): `OneShotResumeSession` keeps the last `StderrTailLines` (5) stderr lines and appends them to the "`<agent>` exited with code N without finishing the turn." error, capped at `StderrExcerptLength` (600) characters. These CLIs explain themselves there — an expired login, an unknown flag, a malformed prompt — and `Debug.WriteLine` is compiled out of Release, so before this the user got an exit code and nothing else. WSL's own `cannot set terminal process group` / `no job control in this shell` lines are filtered out: `bash -ic` without a tty always prints them and they explain nothing.

### Streaming duplication — the trap both stream protocols set

Claude and Cursor both send the answer twice, and naively rendering both prints everything twice:

- Claude: `stream_event` carries token deltas and a complete `assistant` message follows with the same content assembled. `ClaudeStreamParser` takes text/thinking from the deltas and skips them on the assistant message — but only once a delta has *actually arrived* (`_sawDeltas`), not merely because `--include-partial-messages` was requested, so an older CLI that ignores the flag falls back to complete messages instead of showing nothing. Tool calls come from the assistant message, because the deltas only carry fragments of the input JSON.
- Cursor: chunks carry `timestamp_ms`, the whole-answer recap does not. The recap is dropped once a chunk has been seen (`TurnState.SawPartialText` on `OneShotTurnSink.ProtocolState`, which is per turn because the protocol instance is shared across turns) — but kept when no chunk arrived, which is what a resumed turn looks like.
- Codex: `item.updated` repeats the item mid-flight; only `item.completed` is rendered.

### Interruption and permissions (measured, Fase 0)

- Interrupt: `{"type":"control_request","request":{"subtype":"interrupt"}}` → `control_response` → a `user` message with `[Request interrupted by user]` → a `result` with `terminal_reason: "aborted_streaming"`. The process then exits with code 1 — the adapter relaunches with `--resume <session-id>`; it is not an error to show the user. `ParseResult` maps `aborted_streaming`/`aborted`/`error_during_execution` to `WasInterrupted`, so a stop click renders neutrally instead of as a red banner.
- `_interruptRequested` is scoped to the process being torn down, not to a write (v88.0). It is what tells `OnHostExited` that a code-1 exit is the expected end of an interrupt rather than a crash, and it is cleared in `LaunchAsync` — i.e. when the replacement process starts. It used to be cleared in `SendAsync`, so *anything* written between the stop click and the CLI actually exiting (a window of hundreds of ms, and exactly what the v87 `/effort` switch did) turned that exit into a red "The agent process exited unexpectedly (code 1). Restart the agent to continue." and skipped the `--resume` relaunch, ending the conversation. If a new non-prompt write to a live session is ever added, it must not reset this flag.
- Claude stream-json *does* have an interactive permission channel, behind an undocumented flag (measured, v85.0): `--permission-prompt-tool stdio` is absent from `--help` but is what puts `AskUserQuestion` and `ExitPlanMode` in the headless tool inventory at all. Without it both tools are simply missing and the agent answers *"/plan isn't available in this environment"* — the earlier conclusion that the channel did not exist came from testing `control_request/initialize` hooks, which really do not enable it. With the flag the CLI sends `{"type":"control_request","request_id":R,"request":{"subtype":"can_use_tool","tool_name":T,"input":I,"tool_use_id":U}}` and blocks the turn until it gets `{"type":"control_response","response":{"subtype":"success","request_id":R,"response":{"behavior":"allow","updatedInput":I'}}}` (or `{"behavior":"deny","message":…}`).
- `allow` must echo the input back, and for `AskUserQuestion` it must carry the answers: `updatedInput` is the original input plus `"answers": { <question text> : <chosen label> }`, keyed by the question text verbatim. Allowing without that member makes the tool return *"The user did not answer the questions."* — it fails as a no-op, not as an error, so it is easy to miss. `ParseControlRequest` deep-clones the input and grafts the map on.
- `--permission-mode` accepts `acceptEdits`, `auto`, `bypassPermissions`, `manual`, `dontAsk` and `plan`. `ClaudeDangerouslySkipPermissions` maps to `--dangerously-skip-permissions` and, since there is then nothing left to ask, suppresses both `--permission-mode` and `--permission-prompt-tool`; otherwise the mode is `plan` when `ClaudePlanMode` is set and `acceptEdits` otherwise. Plan mode and skip-permissions are mutually exclusive in `CreateClaudeSession` *and* in the two menu handlers, so neither can be left half-set.
- An unanswered request wedges the turn, so `AgentInteractionRequest` is one-shot under a lock (a double-clicked card cannot send two responses), pending requests are denied when the session is interrupted or disposed, and `AbandonPendingInteractions()` closes the cards on the UI side.
- A question with no options falls back to a plain approval card rather than rendering an unsubmittable empty form.
- Tool calls needing approval outside this channel are still silently auto-denied and appear only as `permission_denials` on the final `result` — which is why the UI surfaces them prominently.
- ACP providers get real permission dialogs (`session/request_permission` → `ShowNativePermissionDialog`), which is strictly better than the terminal path. Caveat: Devin uses session modes (`accept-edits`/`ask`/`bypass`) rather than this channel, so it may never fire there.

### UI (`UI/ChatTranscriptView.xaml`, `UI/ChatMessages.cs`)

- Declared in the same grid cell (`TerminalSlotGrid`) as the terminal's `WindowsFormsHost`; `ShowNativeTranscript(bool)` flips visibility — never both. Since v84.0 the view normally does *not* render there: `TryStartNativeModeAsync` moves it into the chat tab as its last step.
- Detach means "chat tab" in native mode (v84.0): `RefreshToolbarLayout()` no longer hides the command (`Apply(ToolbarButton.DetachTerminal, true, ...)`), and `DetachTerminalButton_Click` routes to `ToggleChatTabAsync()` when `IsNativeModeActive`. `UpdateDetachButtonIcon` swaps "Terminal" for "Chat" in the caption and tooltip. This is also the only way back to the tab once the user closes it — since v85.0 the panel shows no placeholder button at all while the chat is in the tab.
- Detach collapses the slot the chat lives in (v83.0): detaching sets `TerminalGroupBox.Visibility = Collapsed` and the terminal row/column `MinHeight`/`MinWidth` to 0 so the prompt can take the whole panel. Since the chat is a sibling of the `WindowsFormsHost` *inside* that group box, a terminal detached earlier left native mode rendering into nothing — the panel showed prompt, toolbar and usage bars with no transcript anywhere, which looked exactly like "the setting did nothing". Three places fix it: `TryStartNativeModeAsync` calls `AttachTerminalAsync(preserveDetachPreference: true)` when `_isTerminalDetached`; `ShowNativeTranscript(true)` restores the group box and `RestoreTerminalSlotMinimumSize()` unconditionally; and the startup auto-restore in `Workspace.cs` skips `DetachTerminalAsync()` while `IsNativeModeActive`.
- The detach preference survives the forced attach (`preserveDetachPreference` keeps `IsTerminalDetached` in the settings file), and `RestartTerminalWithSelectedProviderAsync` re-detaches after `StartEmbeddedTerminalAsync` when native mode is switched back off — so the detached tab comes back rather than being silently forgotten.
- Streaming appends into the *current* view-model's `StringBuilder` via `INotifyPropertyChanged` — never recreate the item, or the list flickers.
- Interaction cards are transcript rows, not dialogs (v85.0): `ChatInteractionViewModel` derives from `ChatMessageViewModel` with `ChatMessageKind.Interaction`, which is the only reason it can enter the `ObservableCollection<ChatMessageViewModel>` and be picked up by the existing template selector. A modal would have been simpler and wrong — the answer belongs in the scrollback, and the card stays after being answered, collapsing to an italic outcome line so a scroll-back explains why the agent did what it did.
- The question text is the wire key, so `ChatQuestionViewModel.Question` is stored and echoed verbatim; rewording it for display would break the answers map (see *Interruption and permissions*).
- Submitting with nothing chosen is a no-op that leaves the card open, rather than allowing with an empty map — the CLI would accept it and burn the turn reporting that nothing was answered. Every question also takes a free-text `OtherAnswer`, which wins over the selected options when non-empty.
- Option buttons reach their parent question through `Tag="{Binding DataContext, RelativeSource=…AncestorType=ItemsControl}"` — the button's own `DataContext` is the option, and single-select needs the sibling list to clear the others.
- The panel's prompt box, `@`-mention, attachments, image paste, custom commands and Enter/Ctrl+Enter are unchanged; only the destination of the text differs.

#### Rendering (v87.0)

- Markdown is rendered, not split (`UI/MarkdownFlowRenderer.cs`): headings, lists (nested, ordered and unordered), block quotes, rules, pipe tables, fenced code and the inline runs (`bold`, `*italic*`, `` `code` ``, links) become a `FlowDocument` shown by `MarkdownBlock`, a read-only `RichTextBox`. `RichTextBox` and not `TextBlock` because .NET Framework's `TextBlock` cannot be selected, and copying an answer is the most common thing done with a chat. It replaced `MarkdownSplitter`, which only knew about code fences.
- Rendering is driven by `RenderedText`, never by `Text`. `Text` changes on every streamed token; binding the document to it would rebuild the whole `FlowDocument` dozens of times a second. `Complete()` publishes `RenderedText` once when the turn ends, and the row shows a plain `TextBox` of `Text` until then (`IsStreaming`).
- Headings scale off the base font size, so `MarkdownBlock` rebuilds its document when `FontSize` changes — the scaled sizes are baked into the document and would otherwise keep the previous scale.
- Links are coloured runs, not `Hyperlink`s: a live hyperlink swallows the click that starts a text selection, which is the whole point of the read-only box. They are still clickable (v107.0): `BuildLink` stamps the URL onto `Run.Tag`, and `MarkdownBlock` compares its `PreviewMouseLeftButtonDown`/`Up` positions — within `ClickDragTolerance` (3 DIPs) counts as a click and hit-tests `Tag` via `GetPositionFromPoint`, anything further is left alone as a selection drag. Neither handler sets `e.Handled`, so the underlying `RichTextBox` selection logic always runs too; a plain click just leaves an invisible caret (`IsReadOnlyCaretVisible` is off). `MarkdownBlock.LinkClicked` bubbles through `ChatTranscriptView.LinkClicked` (wired on all three `MarkdownBlock` instances — the assistant body, the thinking block and the plan-review card) to `OnChatLinkClicked` in `NativeChat.cs`, which opens `http`/`https` URLs with `Process.Start(UseShellExecute: true)` and treats everything else as a file reference, splitting a trailing `:line` or `:line-line2` (`ChatFileLineRefPattern`, greedy so a Windows drive-letter colon does not get mistaken for the split point) and resolving the path via `ResolveChatFileLinkAsync` — tried as typed, then joined to the workspace root, then matched by trailing segment/filename against the same `_atEntries` index the `@`-mention picker builds (agents often cite a bare filename or a path relative to a different root). A match opens through `EnvDTE.DTE.ItemOperations.OpenFile` + `TextSelection.GotoLine`, the same mechanism `DiffViewerControl.OpenFileInEditor` uses.
- Bare URLs and file citations are auto-linked too (v107.0), not just `[label](url)` syntax — measured against a real turn, agents asked for `file.cs:41`-style citations wrote plain text with no brackets around it far more often than markdown links. `AppendInlines` matches `AutoUrlPattern` (`https?://…`, trimmed of trailing sentence punctuation via `TrimTrailingPunctuation`) and `AutoFileRefPattern` (`path/File.ext:123` or `:123-456`, requiring a dot-plus-extension before the colon so "ratio 3:1" or a "10:41" timestamp is never mistaken for a citation) at every `h`/word-start character, and routes a hit through the same `BuildLink` as an explicit link. Bracketed links are matched first (the `[` branch runs before the autolink checks) so nothing double-processes.
- Citations wrapped in a code span are auto-linked too (v108.0): agents just as often write `` `Program.cs:56` `` or wrap a whole line — `` `Program.cs:56 — public async Task Foo()` `` — as one inline-code span, which used to render as a single flat `Run` with `CodeBackground` and no `Tag`, so nothing inside a backtick span was ever clickable. The backtick branch in `AppendInlines` now delegates to `AppendCodeSpanInlines`, which re-runs the same `AutoUrlPattern`/`AutoFileRefPattern` scan over the span's contents: a matched segment becomes a link (`BuildLink`, monospace font kept, no `CodeBackground` — so it reads as a link, not an inert code block) and everything around it keeps the normal monospace-plus-background code styling.
- Selection uses `ChatSelectionBrush`, not the VS theme's `HighlightKey` (v107.0): the theme highlight renders as a saturated violet block in the transcript and fights with the accent-blue link text sitting on it. Both read-only styles (`SelectableTextStyle` for the streaming `TextBox`, `MarkdownBodyStyle` for `MarkdownBlock`) use a translucent tint of `ChatAccentBrush` instead (`#661C8AE0`, with `SelectionOpacity="1"` so the brush's own alpha is the only transparency in play). The composer input and the interaction cards' free-text answer box keep the VS highlight — those are real editable text, where matching the rest of Visual Studio is correct.
- Link colour swaps light/dark independently of `ChatAccentBrush` (v109.0): `#1C8AE0` (the fixed accent used for borders/icons in both themes) reads fine on a light background but is too low-contrast as underlined link text on VS's near-black one. `MarkdownBodyStyle` binds `AccentBrush` to `{DynamicResource ChatLinkAccentBrush}` instead of the static accent; `ChatTranscriptView`'s constructor wires `Loaded` and `VSColorTheme.ThemeChanged` to `ApplyLinkAccentForTheme()`, which reads `VsBrushes.WindowKey`'s luminance (same formula as `DiffViewerControl.DetectTheme`) and writes a brighter blue (`#5BB4FF`) or the original one straight into `Resources["ChatLinkAccentBrush"]`. Because every `MarkdownBlock` row resolves `AccentBrush` through that same `DynamicResource`, one write repaints every link already on screen — and any row rendered afterwards — with no per-instance plumbing.
- Tool cards are one informative line when collapsed (`UI/ChatToolPresentation.cs`, pure and unit-tested in `Tests/ChatToolPresentationTests.cs`): `ChatToolPresenter.Describe(name, inputJson)` returns the icon, title, target (file / command / pattern), a badge (`+12 -3`, `lines 10-14`, `1/2`) and, for `Edit`/`MultiEdit`/`Write`/`NotebookEdit`, a diff built with DiffPlex from `old_string`/`new_string` (all lines added for `Write`). A column of bare "Read"/"Edit" labels said nothing about the turn. Capped at 400 diff rows with 2 lines of context; no line numbers, because the payload is a fragment and any number shown would be wrong. Unknown tools, MCP-prefixed names (`mcp__server__tool`) and renamed arguments must degrade to "name + raw JSON" rather than throw — the inventory changes with every CLI release.
- A running tool row animates (v94.0): `ChatToolViewModel` carries its own `SpinnerGlyph` + `AdvanceSpinner()` over the same `◐◓◑◒` frames as the global status spinner, and `ChatTranscriptView`'s existing 120 ms activity timer advances every row whose `IsRunning` is true — no second timer, since every tool call happens inside a `BeginActivity`/`EndActivity` window so that one is always live when a row can be running. A static "still running" glyph read as frozen on the rows where it matters most: a subagent `Task` card can sit for minutes
- The raw input JSON is only shown when there is no diff (`ShowRawInput`), and tool results are truncated at 20 000 characters — a whole-file `Read` otherwise puts hundreds of kilobytes into a text box and stalls the layout.
- Accent colours are literal, not theme brushes (`ChatToolAccents`, frozen and shared): "this ran a command" and "this line was added" have to mean the same thing under both the dark and the light theme, and the VS palette has no stable key for either.
- Chat font and size are settings, not the console font (`NativeChatFontFaceName` / `NativeChatFontSizePt`, Settings → Terminal): every installed face is offered, proportional ones included, because the transcript is laid out by WPF and not on a character grid. `SetChatFont` writes the `ChatFontFamily` / `ChatFontSize` / `ChatSmallFontSize` / `ChatTinyFontSize` resources, which every template takes as a `DynamicResource` so the secondary sizes move with the base one. Code blocks and diffs keep `ChatCodeFontFamily`. Ctrl+Scroll zoom multiplies on top and is persisted separately (`NativeChatZoom`).
- `ApplyChatAppearance()` is called wherever the transcript becomes visible — the chat tab *and* `ShowNativeTranscript(true)` in the panel — because `UpdateChatComposerState` returns early when the chat is not in its tab, so the panel-hosted case would otherwise never restore font, zoom or composer height.
- Composer: Ctrl+V and Ctrl+↑/↓ (v87.1/v100.0). Ctrl+V raises `PasteRequested`; the parent runs the panel's `TryPasteImage()` and sets `Handled` only when the clipboard really was an image, so ordinary text still pastes. Ctrl+↑/↓ anywhere in the composer walks the prompt history — and history navigation puts the caret at the start, so a second Ctrl+↑ keeps going backwards instead of moving inside the recalled prompt. `NavigateHistoryUp/Down` write to whichever prompt box has the keyboard (`ChatTranscript.ComposerHasFocus`), otherwise the chat tab's Ctrl+↑ would silently rewrite the hidden panel prompt.
- Esc in the composer stops the turn when one is running (v125.0): `ComposerInput_PreviewKeyDown` checks `StopButton.Visibility` — visible means a turn is in flight — and raises the same `StopRequested` event the Stop button does. Idle Esc (no turn running) is a no-op — it does not drop focus to the transcript (that earlier fallback was removed per feedback: unexpected focus loss while idle wasn't wanted). The placeholder hint and the Stop button's tooltip both read "Esc" for the stop behavior only.
- Native mode pins the terminal type to Command Prompt and skips the `wt.exe` availability check: no console is ever launched, so validating one only produced a misleading prompt. It also forces `AgentFinishConfig.IdleSeconds` to 1 and disables that box in the dialog — the protocol says when a turn ended, so there is no idle window to wait out.

#### Live turn clock and end-of-turn summary (v87.0)

- The status line spins and ticks (`BeginActivity` / `SetActivityLabel` / `SetActivityDetail` / `EndActivity` on the view, a 120 ms `DispatcherTimer`): a twenty-minute turn used to show a motionless "Working..." with no way to tell progress from a hang. The spinner is its own `TextBlock` (`StatusSpinner`) so it can carry the accent colour while the text stays muted — one `TextBlock` would mean rebuilding inline runs every frame. `SetStatus` deliberately stops the timer and hides the spinner: it is the "here is a fixed sentence" entry point, and a running clock would overwrite that sentence 120 ms later.
- Spinner frames are Geometric Shapes (`◐◓◑◒`), not the braille cells every CLI spinner uses: braille is absent from Segoe UI and renders only through a fallback font, at a different size and baseline than the text beside it.
- The caption rotates through `WorkingVerbs` every 4 s ("Pondering…", "Percolating…"). An unchanging line reads as frozen, and the clock alone does not say the agent is alive. `SetActivityLabel` pins a caption instead ("Waiting for your answer...", "Stopping..."), which must not drift into "Percolating…" while the user reads the question; passing an empty string hands the line back to the verbs.
- Waiting for an answer changes the caption, not the clock: an interaction card leaves the turn open, and the time spent waiting on the user is part of how long it took.
- Live tokens come from a new `AgentEventKind.UsageUpdated`, emitted by `ClaudeStreamParser.ParseAssistant` from `message.usage` — each assistant message carries the usage of the request that produced it, and a turn with tool calls is many such requests. `ReadUsage` returns null for a missing node rather than a zeroed instance, which the UI would render as "0 tokens" and look like a bug. Adapters whose protocol stays silent until the end simply never raise it and only get the clock.
- Output tokens accumulate across the turn; input does not. Every request re-sends the whole conversation, so the latest one *is* the context size — summing them reports a number several times larger than anything billed.
- `ChatFormatting.Tokens` is one figure, not a breakdown. With prompt caching the input count is almost always a handful of tokens, so `1 in · 577 out · 25,750 cached` read as a bug rather than as information; cache reads are excluded entirely, being context the model did not process again.
- A `✳ Done in 19m 15s · 578 tokens` notice closes each turn, and the status line is cleared rather than settling into the same summary — the two sat adjacent and said the same thing twice. Guarded by `_nativeTurnInFlight` so the spare end-of-turn event the one-shot adapters emit on relaunch cannot post a second footer. `ResolveTurnDuration` prefers the CLI's own `duration_ms`, then the on-screen clock, then the wall clock, so the footer never contradicts the line it replaced.

### Chat tab and composer (`Controls/ClaudeCodeControl.NativeChat.cs`, `ToolWindows/NativeChatToolWindow.cs`)

- The tab is a `ToolWindowPane` registered with `Style = VsDockStyle.MDI` (plus `Transient = true`), which is what puts it in the central document area next to open files rather than in a docked tool-window strip. GUID `C3D4E5F6-A7B8-9012-CDEF-AB3456789012`. No `.vsct` entry — it is opened programmatically, never from a menu.
- The transcript is re-parented, never duplicated. `ShowNativeChatTabAsync` removes `ChatTranscript` from `TerminalSlotGrid.Children` before `SetChatContent(...)`, because a WPF element lives in exactly one visual tree; `ReturnNativeChatToPanel` reverses it. The live session keeps streaming into the same instance throughout, so the conversation survives every move.
- The vacated panel slot is collapsed, not filled (v85.0): `SetPanelTerminalAreaVisible(false)` hides `TerminalGroupBox` and zeroes the terminal row/column minimum size — the same mechanism detach uses — so the panel reads as prompt-only and the prompt gets the space. The 84.0 placeholder ("The chat is open in its own tab" + a button) is gone. It returns early when the terminal is *detached*, because in that case the slot is already collapsed for another reason and `ReturnNativeChatToPanel` must not un-collapse it.
- The pane is transient, so a closed frame is gone: `OnNativeChatWindowClosed` nulls `_nativeChatWindow` so the next open rebuilds it via `FindToolWindow(..., true)`. `CloseNativeChatTab` therefore captures the reference *before* calling `CloseFrame`, since `CloseFrame` fires that same handler synchronously.
- The composer reuses the panel's send path. `OnComposerSendRequested` copies the text into `PromptTextBox` and calls `SendButton_Click` — that is what keeps attachments, prompt history, diff tracking, `AutoOpenChangesViewAsync` and the native early-return behaving identically from both entry points. Duplicating the pipeline was the alternative and would drift.
- Attachment chips are mirrored, not shared. `UpdateImageDropDisplay()` builds one chip per host via `CreateAttachmentChip(path)`; both read `attachedImagePaths`. Same reason as above — one element, one visual tree. Image attachments carry a thumbnail (v97.0) sized by the single `AttachmentThumbnailSize` constant (32 px; the chip height and the decode resolution are both derived from it), built by `CreateAttachmentThumbnail` (ImageHandling.cs) and painted as an `ImageBrush` on a `Rectangle` with `UniformToFill`: a wide screenshot letterboxed into a chip-sized box is a hairline, so the square crops instead. Decoding goes through `LoadThumbnailBitmap`, with `CacheOption.OnLoad` — OnLoad is required, since pasted images live in the session temp folder that cleanup deletes, and a lazily-bound `BitmapImage` keeps that file locked. The chip bitmap (2x the thumbnail size, for 200% DPI) and the hover preview (1200 px, decoded on `ToolTipOpening`) are separate: sharing the chip's bitmap made the preview visibly soft, because `Image` then upscaled 256 px to preview size. For the same reason `DecodePixelWidth` is applied only when the source is wider than the cap — it upscales as readily as it downscales — which is what `GetImagePixelWidth` (header-only read via `BitmapDecoder` + `DelayCreation`) is for. Any decode failure returns null and the chip renders name-only; a corrupt attachment must still be visible and removable.
- Live switching keeps the conversation via resume. `RelaunchNativeSessionAsync` captures `_agentSession.ResumableSessionId` (not `SessionId` — see below), calls `DisposeNativeSession()`, puts the id in `_pendingResumeSessionId`, rebuilds the session and deliberately does not call `ChatTranscript.Clear()` — the transcript reads as one thread with a `ChatMessageKind.Notice` divider marking the switch. Claude consumes the id in `CreateClaudeSession`; Codex consumes it in `CreateOneShotSession`. Adapters without resume support say the conversation starts over. `_nativeSwitchInProgress` guards against overlapping relaunches.
- Two dropdown changes in a row must not resume an id the CLI never created (v88.0). `IAgentSession.ResumableSessionId` is the id a relaunch may hand to `--resume`, and it is *not* `SessionId`: the extension generates the Claude session id itself and passes it as `--session-id`, but the CLI writes no transcript until a turn actually runs (measured: it emits nothing at all at launch; `system/init`, which confirms the id, arrives with the first turn). So after any relaunch with no prompt in between, `SessionId` is still an unused seed, and `--resume`-ing it fails the launch outright — `No conversation found with session ID` on stderr, an `error_during_execution` result, then exit 1. On screen that read as "Turn interrupted." followed by "The agent process exited unexpectedly (code 1)" and a dead input pipe, and it fired on the *second* consecutive change of any composer dropdown (model, effort, permission, plan mode), since all of them go through `RelaunchNativeSessionAsync`. `ClaudeStreamJsonSession` therefore tracks `_sessionIdConfirmed` (set on `SessionStarted`) and returns the confirmed id, else the id it was itself launched to resume, else empty; empty means "launch fresh with `--session-id`", which loses nothing because nothing ran. Its own two internal relaunch paths (`EnsureRunningAsync`, the interrupt recovery in `OnHostExited`) use the same property. The other adapters only ever learn their id from the agent, so for them it is `SessionId` unchanged (`PrintModeSession` has none and returns empty).
- Effort is a launch flag like the model (v88.0), so switching it relaunches-and-resumes through the same `RelaunchNativeSessionAsync` path. `GetNativeEffortArgument()` lowercases the enum into `--effort`; `EffortLevel.Auto` maps to the empty string because it is the extension's own "say nothing" and the one value the CLI rejects (every slider level — including the undocumented `ultracode` — is accepted; an unknown one only warns on stderr and falls back to the default). Until v87 this was `/effort <level>` sent over the structured channel instead, which had two defects: the CLI applies the command "for this session only", so every other relaunch (model, permission, plan, interrupt recovery) silently reverted the level while the composer still showed it; and it was the only non-prompt write to a live session, which is what made `SendAsync` clobber `ClaudeStreamJsonSession._interruptRequested` (see *Native Mode — Agent Sessions*). The terminal path still uses `/effort`, correctly — it drives an interactive TUI.
- Effort is the pill slider, not a dropdown (v85.0): it reuses the panel's `EffortFromSliderIndex`/`EffortToSliderIndex` ordering so both surfaces agree on what index 2 means. Everything else stayed a dropdown; only effort has a natural ordering to slide along.
- The composer's effort slider commits on popup close, not per stop (v89.0): `EffortChanged` is raised from `EffortPopup_Closed` when the stop differs from the one recorded in `EffortPopup_Opened` — nothing is reported while the popup is open. Committing per stop (v85–v88 did, on `ValueChanged` for clicks/keys and `Thumb.DragCompleted` for drags) relaunched the agent while the user was still choosing: a click on a stop two positions away, or an arrow-key walk, fired a relaunch per stop and the chat froze under the pile-up. `ValueChanged` now only tracks the index and captions it from `SetEffortStopLabels` (the parent's `GetChatEffortStopLabels()`, slider-ordered) — the parent's own caption via `SetEffortSlider` only arrives *after* a level is applied, so without the stop labels the popup would show a stale level while the thumb moved. `SetEffortSlider` re-baselines `_effortIndexOnOpen` only while the popup is closed, so a level applied elsewhere mid-interaction cannot make the user's own pick look unchanged. The panel's slider keeps its drag-deferred commit: `/effort` to a TUI is cheap and does not relaunch anything.
- Plan mode is a launch flag, so toggling it relaunches (resumed, so the conversation so far becomes the plan's input). Approving an `ExitPlanMode` card clears `ClaudePlanMode` — that is how a session leaves planning; without it the next relaunch would silently put the agent back into planning right after the user said go ahead.
- Provider labels are qualified by `GetChatProviderDisplayName` (" (WSL)" / " (native)"), used by the menu, the caption and the switch notice alike — the raw display names collide for the paired providers, so the menu showed two identical entries.
- Native-mode sessions can be renamed from the tab (v125.0), reusing the Session History rename infra (issue #95) rather than a separate mechanism: the ✎ composer button and the clickable `SessionTitleBar` header (`ChatTranscriptView.xaml`, docked above `TranscriptScroll`, collapsed when there is no custom title) both raise `RenameSessionRequested`. `OnComposerRenameSessionRequested` (NativeChat.cs) reads `_agentSession.SessionId`, opens the same `ShowRenameSessionDialog` the History dialog uses (built a throwaway `SessionInfo` just to carry the id and current title), and writes the result into `_settings.SessionCustomTitles` keyed by that id — the exact dictionary the History dialog reads, so a title set from either surface shows up in both. The VS tab caption stays plain (`provider + " Chat"` — the tab strip is too narrow and truncated longer titles awkwardly); instead `UpdateChatTabCaption` calls `ChatTranscript.SetSessionTitle(GetCurrentNativeSessionTitle())` to show/hide the header and set its text, and is re-run on every `AgentEventKind.SessionStarted` (cheap, idempotent — that event fires once per turn, not once per conversation) so a resumed session's saved title appears as soon as its id is confirmed, not only after an explicit rename in the tab. Renaming is a no-op with an explanatory message when the id is still empty — either the session has not run its first turn yet, or the adapter never exposes one (Antigravity), in which case there is nothing to key the title on. Codex reports its id on the first completed turn and, since v132.0, exposes a selected history id immediately on resume.
- Each session has its own accent color, keyed the same way as the title (v125.0): two entry points raise the shared `ColorPickerRequested` event — the 12x12 `Border` swatch (`SessionColorSwatch`, docked right inside `SessionTitleBar`, own `MouseLeftButtonUp` with `e.Handled = true` so the click doesn't also bubble to the bar's rename handler) and `ComposerColorButton` (🎨, composer bar, next to the ✎ rename button) — the composer one exists specifically so the color can be changed without renaming first, since the header (and its swatch) stays collapsed until a title is set. `OnComposerColorPickerRequested` (NativeChat.cs) opens a plain `System.Windows.Forms.ColorDialog` (`FullOpen = true`, no hex box — one native picker, matching the ask) seeded from `_settings.SessionTitleColors[sessionId]` (falls back to `#1C8AE0`) and writes the chosen `#RRGGBB` back into that dictionary. `SetSessionTitleColor` (`ChatTranscriptView.xaml.cs`) mutates the shared `ChatAccentBrush` resource's `Color` in place rather than reassigning individual elements' Foreground/Background: every element in the view that references it via `{StaticResource ChatAccentBrush}` (user message bubble borders, the welcome banner border/heading/tips-list icons, and the session title text + swatch) holds that exact same `SolidColorBrush` instance, so one mutation live-updates all of them — this is what makes the picker recolor "everything blue" in the tab, not just the title, without threading the color through every template. An empty/invalid entry resets the shared brush back to the default blue (`DefaultAccentColor`, `#1C8AE0`). Applied the same way title text is: from `UpdateChatTabCaption`, called on every `SessionStarted` so a resumed session's saved color reapplies without an explicit re-pick. The brush lives in `ChatTranscriptView`'s own `UserControl.Resources` (not a merged app-wide dictionary), so each chat tab instance mutates its own copy — no cross-tab bleed.
- Zoom is a `LayoutTransform` (`RenderTransform` would blur and would not re-flow the text) driven by Ctrl+Scroll, and it plus the composer height are persisted (`NativeChatZoom`, `NativeChatComposerHeight`) and re-applied by `UpdateChatComposerState`.
- New chat is a confirmed relaunch with `forceNewSession: true`, which is the one path that deliberately skips `--resume` and clears the transcript.
- The welcome card is the extension's own startup banner (v88.0) — `ShowChatWelcome(workspace)` → `ChatTranscript.ShowWelcome(title, facts, tips)`. Native mode never sees the CLI's greeting: the agent runs headless and its banner is not part of the event stream, so an empty transcript said nothing about what was running. Shown from exactly two places — after `session.StartAsync` in `TryStartNativeModeAsync`, and at the end of `RelaunchNativeSessionAsync` only when `forceNewSession`, since a model or permission switch keeps the conversation and a fresh-start card mid-thread would read as if it had been thrown away. It lives inside the scroll content above `MessagesList` (not layered over it, which would cover the first answer) and is dropped by `OnMessagesChanged` on the first `IsUser` row — not on the first row of any kind, or the "New chat" notice posted by the same relaunch would erase it immediately. `Clear()` hides it, leaving the caller to decide whether a new conversation is starting.
- The CLI version is probed in the background, never awaited. `BeginCliVersionLookup` runs `<cli> --version` (WSL: `wsl.exe bash -lic "<cli> --version"`, a login shell for the same reason the session launch uses one) with the executable resolved exactly as the launch resolves it, so the number shown is the one actually running. Results are cached in a static `ConcurrentDictionary<AiProvider, string>` where an empty value means "asked and got nothing" — that is what stops a missing or slow CLI from being probed again on every new chat. Both pipes are read asynchronously with `BeginOutputReadLine`/`BeginErrorReadLine` and the process is killed after 5 s: `StandardOutput.ReadToEnd()` on a CLI that never exits would strand a pool thread forever. The redraw is guarded by `ChatTranscript.IsWelcomeVisible` and a provider re-check, so a late answer cannot resurrect a card the first prompt already dismissed. `ExtractVersion` regexes the first version-shaped token out of the output because the CLIs disagree on the format (`2.1.220`, `codex-cli 0.5.0`, …).
- Facts and tips claim only what the chat can actually do. Model and effort are listed only for the agents whose choice the extension owns (the same condition as `SetSelectorAvailability`), and the tips cover ↑-history, Ctrl+V, Ctrl+Scroll, the selectors and ✚ — deliberately *not* `@`-mentions or slash commands, which the composer does not implement. The mascot is drawn as `Rectangle`s in a `Viewbox` rather than typed as an emoji or a glyph: a missing font renders as an empty box, and its eyes are punched out in `ToolWindowBackgroundKey` so it reads the same under both themes.
- Provider switches are not resumable by definition (no two agents share a transcript), so they go through `RestartTerminalWithSelectedProviderAsync()`, which tears native mode down and starts it again — closing and reopening the tab on the way. `UpdateProviderSelection()` must run again *after* that call (v94.0): the pre-switch refresh still reads the outgoing agent off `_currentRunningProvider` (per the *Active provider UI rule*), so without the second call the tool-window caption kept the old provider name for the rest of the session.
- A failed provider switch used to look exactly like a successful click doing nothing (fixed v113.0): `RestartTerminalWithSelectedProviderAsync` → `TryStartNativeModeAsync` swallows its own failures internally (falls back to the embedded terminal, or leaves native mode off) and any exception surfacing past that only reached `OnChatProviderSelected`'s catch block, which logged to `Debug.WriteLine` only — invisible outside a debugger. Worse, the "🤖 Switched to X" notice fired unconditionally after `await RestartTerminalWithSelectedProviderAsync()`, regardless of whether the switch actually happened. `OnChatProviderSelected` now checks `GetActiveOrSelectedProvider() == provider && _chatIsInTab` before claiming success, posting a `ChatMessageKind.Error` card instead when it does not match, and the catch block posts one too instead of only logging.
- Every agent has a model menu in the composer (v111.0): `BuildChatModelMenu` hands any non-Claude provider to `FillChatModelMenu`, which lists the cached catalog plus an "Agent default" entry and, when the cache is stale, shows a disabled "Loading models…" row and refills the *open* menu when the fetch lands (the continuation bails out if the menu closed or the provider changed meanwhile). `GetChatModelLabel` shows the pick on the button; `UpdateChatComposerState` now enables the button for `IsClaudeProvider(provider) || ProviderHasModelCatalog(provider)`. See *Model Catalog & Selection*.
- A model pick that can't be applied live offers a restart (v98.0, generalized v111.0): `OnChatProviderModelSelected` records the model and, when `SetModelAsync` could not switch the running session (see the v102.0 ACP note above), asks whether to restart the chat now — Yes relaunches with `forceNewSession: true`, No posts the "applies the next time the agent starts" notice. The relaunch is deliberately *not* resumed: ACP has no resume, so pretending otherwise would silently drop the conversation instead of saying so.
- Composer menus are built per click (their contents depend on the running agent, which can change between two clicks) and styled from `UI/ChatStyles.xaml` — `ComposerMenuStyle`/`ComposerMenuItemStyle`, looked up with `ChatTranscript.TryFindResource`. Default WPF menu chrome (checkbox gutter, white border) does not belong in a themed VS tab. Note the SDK has no `CommandBarMenuItemMouseOverKey`/`CommandBarMenuItemMouseOverTextKey` — the highlight uses `CommandBarHoverOverSelectedKey` + `CommandBarTextActiveKey`; the wrong keys only fail at XAML compile time. Model/effort/permission buttons collapse for agents where the extension does not own the choice (`SetSelectorAvailability`).
- Typed selector commands (v89.0): `/plan`, `/model` and `/effort` are the extension's own commands, intercepted in `SendButton_Click` by `TryHandleNativeSelectorCommand` *before* the prompt is assembled — which is why they work from the chat composer and the panel's prompt box alike (the composer hands its text to that same path). Gated on `IsNativeModeActive`, on the active provider being Claude (the other agents have no plan mode, no effort level, and pick their model inside a TUI native mode cannot reach), on there being no attachments, and on an exact match of the trimmed text — `/plan the migration` is a prompt about planning and taking it as a command would silently swallow it. `/plan` calls `OnChatPlanModeSelected(true)`, which no-ops when already planning, so that case posts its own "Already in plan mode." notice rather than making the text vanish with nothing to show. `/model` and `/effort` open the composer menus through `ShowChatSelectorMenu`, anchored via `ChatTranscriptView.GetSelectorAnchor(selector)` — the matching composer button, or null when the composer is hidden (transcript back in the panel) or that selector does not apply, in which case the panel's send button anchors it. `/effort` deliberately opens `BuildChatEffortMenu()` rather than the pill slider: the slider is a `Popup` anchored to `ComposerEffortButton`, which does not exist in the panel host. Sending these on as prompts is what happened before — the agent answered as if asked about the word.
- `/btw <question>` — side questions (v89.0): the one typed command that takes an argument, so it is matched by prefix (`/btw` followed by whitespace or nothing; the bare form prints the usage line instead of asking an empty question). The headless CLI refuses it outright — *"/btw isn't available in this environment"*, because it is a `local-jsx` command needing the Ink TUI — so `AskSideQuestionAsync` (NativeMode.cs) implements it: a second, short-lived CLI launched with `ClaudeCommandBuilder.GetSideQuestionArguments`, which is plain `--print` plus `--resume <id> --fork-session`. The fork is the whole mechanism — measured against a real session, it reads the entire conversation for context while writing to a *new* session id, leaving the live transcript byte-identical (340244 bytes before and after) so the running turn never meets a second writer. Plain `--print` means the answer is text on stdout, no event stream to parse. It runs completely outside the turn machinery: no busy state, no activity clock, no "On Agent Finish" — a side question is not a turn, and one asked mid-turn must not disturb it. `_nativeClaudeOptions` (captured in `CreateClaudeSession`, cleared at the top of `CreateAgentSession`) supplies the same executable, distro, folder and model; the resumable id comes from `IAgentSession.ResumableSessionId`, and with no id the question is asked without context rather than not at all. Bounded by `SideQuestionTimeoutMs` (180 s).

### Parallel chat sessions (`Models/NativeChatSessionState.cs`, v126.0)

- The ✚ button opens a genuinely independent session, not a second view of the same one: `CreateAndRegisterSession` builds its own `IAgentSession`, its own `ChatTranscriptView` and its own `NativeChatToolWindow`, obtained from `package.FindToolWindow(typeof(NativeChatToolWindow), session.WindowId, true)` with a per-session `WindowId` — reusing id 0 would hand back the tab the first session already lives in. Everything a turn mutates (streaming rows, pending tool calls, turn clock, token counters, finish config, rate-limit notice, Codex queue, `CancellationTokenSource`) moved out of the `_...` fields into `NativeChatSessionState`, keyed by `SessionId` in `_nativeSessions` under `_sessionLock`. The panel's own session keeps using the original fields and is *not* in that dictionary.
- Agent events reach the right transcript through a captured closure. Each session subscribes with an `EventHandler<AgentEvent>` that closes over its `sessionId` and is stored in `NativeChatSessionState.EventHandler` — `Received -= (s, e) => ...` would allocate a new delegate and unsubscribe nothing. The same trap applies to `_sessionSendHandlers` / `_sessionClosedHandlers` in NativeChat.cs, which exist purely so the composer's `SendRequested` and the window's `Closed` can actually be detached in `OnSessionWindowClosed`.
- The `...ForSession` helpers must stay faithful ports of the originals. Every symptom of the first pass traced to one divergence: `FinishStreamingMessages` setting `IsStreaming = false` instead of calling `Complete()` left assistant text blank (only `Complete()` publishes `RenderedText`); appending with `target.Text += text` instead of `target.Append(text)` bypassed the `StringBuilder` that `Complete()` reads from; `CompleteNativeTurnForSession` omitting `SetBusy(false)` / `EndActivity(string.Empty)` left the spinner running forever and the Stop button stuck; and `ApplyNativeRateLimitForSession` dropping the early return for a `"allowed"`/empty status printed a bogus "Rate limited: allowed" line on every turn, since that is the status a *non*-limited request reports.
- Handlers that act on "the current chat" resolve the owner from `sender`. `ResolveSessionFromSender(object)` matches the raising `ChatTranscriptView` against `_nativeSessions` and returns null for the panel's own transcript, which is what lets Stop/ESC (`InterruptNativeAgentAsync(sessionId)`), rename, the color picker and the attachment handlers act on the tab the user clicked in rather than always on the first session.
- Model, effort and provider selectors are disabled in the extra tabs (`SetSelectorAvailability(model: false, effort: false, permission: true)`): those do not merely set state, they relaunch through `RelaunchNativeSessionAsync`, which still operates on the global `_agentSession`/`_settings` — wiring them per tab restarted the *first* session instead. Making them per-session means making the relaunch path session-aware.
- Captions and the session header are per tab (v127.0): `NativeChatSessionState.Window` holds the hosting pane so `UpdateSessionTabCaption(session)` can set both its VS caption (`BuildChatTabCaption`, `"<Provider> Chat — <title>"`) and its transcript's own header/accent, keyed by that session's `AgentSession.SessionId`. It runs on every `SessionStarted`, for every session — not just the active one — because a saved title is only resolvable once that agent confirms its id, and each session has a different one.
- Attachments are per session (v127.0): `NativeChatSessionState.AttachedFiles` replaces the shared `attachedImagePaths` for the extra tabs. `OnComposerAttachRequested` / `OnComposerFilesDropped` / `OnComposerPasteRequested` route through `ResolveSessionFromSender` and fall back to the panel's global list when there is no owner. This is what `TrySaveClipboardImage`, `PickAttachmentFiles` and the `CreateAttachmentChip(path, Action<string> onRemove)` overload were extracted for — the chip's ✕ has to know which list it is removing from. `OnSessionComposerSendRequested` builds the prompt with `BuildAttachmentPromptBlock` (extracted from `SendButton_Click`, so both paths share one implementation of the "Files attached:" header and the per-prompt temp copy) and clears the list only after the send.

### Integration with the rest of the extension

- `SendTextToAgentAsync(text)` is the single bifurcation point for every non-prompt-box sender (build errors, runtime errors, custom commands, On-Agent-Finish follow-up and its `SendToAgent` action): native → structured channel, otherwise `SendTextToTerminalAsync` exactly as before. Terminal-only traffic deliberately still calls `SendTextToTerminalAsync` directly — slash commands, the Caveman install — because none of it means anything to a structured session.
- Automated sends target the focused chat tab, not always the first session (v130.0): with several parallel sessions open, `ResolveFocusedNativeSessionId()` (NativeMode.cs) reads `_lastFocusedNativeSessionId`, and `SendTextToAgentAsync` routes to that session via `SendPromptToNativeAgentAsync(text, sessionId)` when it names a still-live one, falling back to the default `_agentSession` path otherwise. Unlike the composer's own sends (which resolve the owner from the raising control — see `ResolveSessionFromSender` above), an automated send has no UI element to read the owner from, so focus has to be tracked separately as the user moves between chats.
- Focus is tracked from keyboard focus, not from the frame notification (v130.0): `MarkNativeSessionFocused(sessionId)` is called from `ChatTranscriptView.IsKeyboardFocusWithinChanged` (wired by `WireTranscriptFocusTracking`, per session plus once for the default transcript inside `WireChatComposer`). `NativeChatToolWindow.Activated` alone is not enough and was the first attempt's bug: it comes from `IVsWindowFrameNotify.OnShow` / `FRAMESHOW_TabActivated`, which VS raises only when switching between tabs in the same tab group. Running one chat docked to the side and another in the document area — a normal two-session layout — leaves both panes visible simultaneously, so clicking between them fires no frame notification at all and the tracked id never moved off the default session, sending everything to the first tab. The `Activated` handler is kept as a second signal for the same-tab-group case. Only the transition *into* focus marks; losing it never clears, otherwise clicking into the code editor would bounce the next build error back to the default tab. A brand-new tab is also marked focused immediately on creation rather than waiting for any event, so an error landing before the user clicks anything still goes to the tab they just opened; closing the focused tab resets the id to the default sentinel (`null`).
- Update Agent works in both modes (v115.0): `UpdateAgentButton_Click` (`Terminal.cs`) checks `IsNativeModeActive` first and routes to `UpdateNativeAgentAsync()` (`NativeChat.cs`) instead of typing into the console. Native mode has no console session to type the CLI's self-update command into, so it runs the update in its own visible `cmd.exe /k` window via `GetNativeAgentUpdateCommand(provider)` — the same command text as the terminal-mode switch, minus the exit sequence, since there is no TUI to exit. The call is wrapped as the `midRelaunchAsync` hook of `RelaunchNativeSessionAsync`: the existing agent process is killed first (an update installer overwriting its own running executable fails — measured with Devin native, which force-kills stragglers before its installer script runs), the method then awaits the update window's exit with no timeout (the user closes it when done reading the output), and only then does `RelaunchNativeSessionAsync` create the replacement session and resume the conversation. `midRelaunchAsync` runs between `DisposeNativeSession()` and session creation specifically so the update always sees the old process gone but the new one not yet started.
- `StartUpdateWindow` hosts every provider's update in `cmd.exe /k` except Devin native (v115.0): Devin native's updater (`taskkill /f /im devin.exe; irm https://cli.devin.ai/install.ps1 | iex`) used to run nested inside `powershell -NoProfile -ExecutionPolicy Bypass -Command "..."`, and Windows Defender flagged that exact shape — bypassed execution policy plus a download-and-execute pipeline is a classic malware heuristic. Devin's own documented update command carries neither flag, so `DevinNative` alone is hosted in `powershell.exe` directly (`-NoLogo -NoProfile -NoExit -Command <command>`, the command passed unwrapped since PowerShell reassembles its own remaining argv the same as typing at a prompt), removing the nested invocation and the flags along with it. Every other provider stays on `cmd.exe /k` — hosting them all in `powershell.exe` was tried first and broke every WSL provider: their commands are written for `cmd.exe`'s own parser (`wsl bash -lic "..."` quoting, `&` chaining), which PowerShell's argument reassembly does not parse the same way, so the update process launched but did nothing and the relaunch that follows brought the agent straight back with no update having run — reported as "the WSL update stopped working, it just reopens the agent". The terminal-mode equivalent (`UpdateAgentButton_Click`, `Terminal.cs`) types into an existing `cmd.exe`-hosted console for every provider including Devin native, so it keeps `&` for chaining and dropped only the unnecessary `-NoProfile -ExecutionPolicy Bypass` flags. Two problems apply to both hosts in native mode: some locked-down machines deny a direct `Process.Start` of a shell for a non-elevated Visual Studio (Software Restriction Policy / AppLocker rules commonly exempt elevated processes) — measured as a `Win32Exception` "Access is denied" before any window appeared, fixed by falling back to `UseShellExecute = true`, which routes through the OS shell launch broker instead of a raw `CreateProcess` call and is not subject to the same restriction. And `WorkingDirectory` is pinned to `Path.GetTempPath()` on both launch attempts rather than left to inherit Visual Studio's current directory, removing that as a second possible source of the same error.
- On Agent Finish fires on `TurnCompleted`, the biggest robustness win of the feature: the config is captured at send time (`_nativeTurnFinishConfig`, mirroring how the watcher is armed at send time so a mid-turn settings change can't retarget it), cleared as it fires so a stray end-of-turn event from a relaunched one-shot adapter can't run the action twice, and skipped when `WasInterrupted` (a cancelled turn is the user stopping, not the agent finishing — building on a half-applied edit would be actively harmful). Duration comes from the CLI's own `duration_ms`, wall clock only as fallback. The entire `AttachConsole`/screen-hash/idle machinery is disarmed: `ArmAgentCompletionWatcherAsync()` returns immediately when `IsNativeModeActive`, and the BuildErrors/RuntimeErrors arm sites are guarded too.
- Rate limits — no percentages (deviation from the original plan): `rate_limit_event` carries `status`, `rateLimitType`, `resetsAt` and `isUsingOverage` but no usage percentage, which is exactly what the inline bars render. `ApplyNativeRateLimit` therefore refreshes the matching bar's *reset label* and raises a transcript notice when the status is not `allowed` (deduped via `_lastNativeRateLimitNotice`, since the CLI repeats the event every turn while the window stays hot). Bar percentages still come from the scraped snapshot — do not invent a fill value from this event.
- Cost of the one-shot adapters: startup latency is paid per message and the provider's prompt cache does not carry over. Inherent to the transport, not to the code; revisit when `codex app-server` leaves experimental.

### Not validated end-to-end

Codex (login expired) and PI (no API key) could not complete a turn on the development machine. Their item payloads were read from the binaries' own serializer names and their handlers ignore anything unexpected rather than failing, so a slightly different shape degrades instead of breaking. WSL launch of the stream-json path is also still unverified.

Antigravity, validated (v95.0): run against a real `agy` install, `agy --print` was found to ignore the launched process's working directory for its own "workspace" concept — without being told explicitly it reports no active workspace and offers to scaffold a project under its own `scratch` folder instead of seeing the folder VS opened. Confirmed fix: pass `--add-dir "<workingDirectory>"` on every turn (`PrintModeCommandBuilder.GetArguments`, `PrintModeSession.cs`) — every turn is a fresh process, so this can't be done once at session start. `--continue` still keys off the CLI's own most-recent-conversation state, unaffected by this.

## Cross-Cutting Rules

These three rules apply across many files — keep them in mind before editing provider selection, UI captions, terminal focus, or anything that sends text to the agent.

Active provider UI rule (v24.0): provider checkmarks, tool-window captions, model/usage menu visibility, detached-tab caption, and visible-agent "active" labels must use `_currentRunningProvider` when a terminal is alive, falling back to `_settings.SelectedProvider` only before launch. Successful provider launches sync `_settings.SelectedProvider` in memory, but `SaveSettings()` still preserves provider/model/effort fields from disk during normal operation so multiple VS instances do not overwrite each other's selections.

Agent send rule (v82.0): any new code that hands the user's or the extension's text to the agent must go through `SendTextToAgentAsync()`, not `SendTextToTerminalAsync()` — native mode has no console, so a direct terminal call silently sends nothing. The exceptions are things that only mean something to a console session (slash commands, CLI self-updates, plugin installs), which keep calling the terminal directly. Likewise, any new console-scraping logic must bail out when `IsNativeModeActive`.

Terminal focus rule (v26.0): do not focus the embedded terminal with direct `SetForegroundWindow(terminalHandle)` or bare `SetFocus(terminalHandle)` calls. Use `FocusTerminalForInputAsync()`, `FocusTerminalForInput()`, or `FocusTerminalWindow()` so VS activates the owning tool window, focuses the WinForms host panel, and temporarily joins the VS UI thread with the terminal window thread before setting native focus. Low-level hook focus checks must stay Win32-only and use cached root-window state; do not touch WPF/WinForms controls from the hook thread.
